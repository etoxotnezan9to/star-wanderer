# Средства комплекта: назначение и вызов

Описание средств, которые лежат в `kit/.branch-kit/tools/` и
копируются в репозиторий вместе с комплектом. По нему пишут сами
средства и `tools/README.md` для их пользователей. Здесь — что делает
каждое средство, как вызывается, что читает из настройки, что выводит и
с каким кодом завершается; как оно устроено внутри, решает автор
средств. Ссылки «AGENTS.md, 4.7» ведут на
[kit/AGENTS.md](../kit/AGENTS.md), «настройка» — на
[kit/.branch-kit/config.yaml](../kit/.branch-kit/config.yaml).

## 1. Общее для всех средств

### 1.1. Перечень

| Средство | Что делает | Кто запускает |
|---|---|---|
| `check_repo.py` | выполняет проверки из настройки, последней строкой — итог для «Чем проверено» | автор, проверяющий |
| `check_docs.py` | проверяет формат документов по настройке | все, обычно как проверка из настройки |
| `poll.py` | опрос: ждёт события в очереди роли и завершается на нём | постановщик, автор, проверяющий |
| `check_merge_log.py` | проверяет журнал слияний основной ветки | все |
| `owner_protect_branches.py` | ставит защиту веток задач, сверяет защиту основной ветки и настройки слияния | только владелец |
| `owner_check_settings.py` | проверяет настройку площадки попыткой | только владелец |

### 1.2. Что нужно и откуда запускать

1. Python 3.8 или новее и PyYAML 5.1 или новее; других зависимостей нет,
   кроме git 2.x и доступа к площадке у средств, которые к ней
   обращаются. Средства работают в Windows и Linux одинаково.
2. Средство запускают из корня клона репозитория командой
   `python .branch-kit/tools/<средство>`; в Linux вместо `python` пишут
   `python3`, в Windows, если `python` не находится, — `py -3`
   (AGENTS.md, вводная часть перед разделом 1). Так же, с `python`,
   написаны вызовы средств ниже.
3. Вывод — в UTF-8, в том числе в Windows PowerShell 5.1.

### 1.3. Настройка

Каждое средство читает `.branch-kit/config.yaml` своего клона; ключ
`--config <файл>` задаёт другой файл. До любого действия средство
сверяет настройку и при нарушении завершается с кодом 2, назвав поле:

1. Файл разбирается `yaml.safe_load`, обязательные поля есть и нужного
   вида: строка, число, список, `true` или `false`.
2. В значениях не осталось места вида `<…>`: незаполненная настройка не
   годится ни для одного средства. В образце слова знаки регулярного
   выражения — имя группы в `(?P<имя>…)`, начало `(?<=…)` и `(?<!…)` —
   местом не считаются.
3. Неизвестное поле — нарушение: опечатка в имени поля иначе молча
   выключила бы его.

Сверку настройки отдельно, без другой работы, выполняет
`check_repo.py --config-only`.

### 1.4. Ключ и площадка

1. Средства, которые обращаются к площадке, берут ключ из переменной
   `GITLAB_TOKEN`, поданной на одну команду (AGENTS.md, 4.2, 6.3),
   например так:

   ```
   # Linux и Git Bash
   GITLAB_TOKEN="$BRANCH_KIT_AUTHOR_TOKEN" python .branch-kit/tools/poll.py --role author --mr 12
   # Windows, PowerShell
   try { $env:GITLAB_TOKEN = $env:BRANCH_KIT_AUTHOR_TOKEN; python .branch-kit/tools/poll.py --role author --mr 12 } finally { Remove-Item Env:GITLAB_TOKEN -ErrorAction SilentlyContinue }
   ```

   `owner_protect_branches.py` — так же, ключом владельца. Исключение —
   `owner_check_settings.py`: переменную `GITLAB_TOKEN` он не читает и
   убирает из окружения git, ключи ролей ему подают файлами, а ключ
   владельца ему не нужен (раздел 7).
2. Ключ не печатается ни в выводе, ни в сообщениях об ошибке, ни в
   адресе. Ключ — только печатные знаки ASCII без пробелов; пробелы,
   перевод строки и возврат каретки по краям отбрасываются; ключ с
   другими знаками или с меткой порядка байтов — отказ с кодом 2 до
   первого обращения к площадке, и метку причина называет отдельно.
3. Площадка — из настройки, поле `площадка`, `адрес`; ключ `--host`
   задаёт другую.
4. Средство, которое действует за роль (`poll.py`, владельческие),
   первым обращением узнаёт учётную запись ключа и сверяет её с
   настройкой, поле `учётные записи`: чужая учётная запись — отказ с
   кодом 2 (AGENTS.md, 6.6). У проверяющего частей ключ — учётной
   записи одного из авторов: агент разработчика работает под ней
   (AGENTS.md, 1.5, 3.7); вызов — `poll.py --role reviewer --target`.
5. Переадресацию площадки средства не выполняют: urllib перенёс бы ключ
   на новый адрес, в том числе на другой узел, а ответ чужого узла
   средство приняло бы за ответ площадки. Ответ переадресацией — отказ с
   кодом 2; в причине — куда она вела.
6. Ключи шифрования TLS средства в файл не пишут: переменную окружения
   `SSLKEYLOGFILE`, по которой Python пишет их по умолчанию, их контекст
   TLS не читает, и файла по ней средства не создают. Сертификат и имя
   узла площадки по https сверяются так же, как Python той же версии
   сверяет по умолчанию.

### 1.5. Вывод и коды выхода

Каждое нарушение — отдельная строка: где, вид нарушения, что не так.
Последняя строка — итог. Коды выхода, кроме `poll.py` (раздел 4):

| Код | Что значит |
|---|---|
| 0 | нарушений нет; у владельческих средств — всё как нужно |
| 1 | есть нарушения или расхождения |
| 2 | проверка не выполнена: нет PyYAML, настройки, ключа, ответа площадки, настройка не сверилась; причина — в потоке ошибок. У `check_repo.py`, `check_docs.py` и `check_merge_log.py` — и необработанный сбой, исключение Python, которого средство не ждало: трассировки нет, в потоке ошибок — его вид и текст, ключ, если попал в текст, заменён на `<ключ>` |
| 130 | прервано сочетанием Ctrl+C — у `check_repo.py`, `check_docs.py`, `check_merge_log.py` и `owner_protect_branches.py`; у `owner_check_settings.py` кода 130 нет: прерванный до первой отправки запуск — код 2, после неё — код 1 (раздел 7) |

Списки площадка отдаёт страницами, следующую называет заголовок
`X-Next-Page`. Заголовок есть и пуст — конец выдачи, в том числе при полной
странице; заголовка нет при неполной странице — тоже конец. Сбой площадки:
заголовка нет вовсе при полной странице; номер следующей страницы не больше
текущей или не номер.

### 1.6. Разобранные исключения

Нарушение, которое нарушением не является, разбирают записью в
`.branch-kit/exceptions.yaml`: средство, место (файл, запрос или
изменение основной ветки), вид нарушения, необязательно абзац и
обязательно причина. Записи лежат
списком в поле `исключения`; в комплекте список пуст, а над ним —
подсказки полей. Исключение без
причины и исключение, которое при полной проверке ничего не покрыло, —
нарушения. Новое исключение — решение: его вносят запросом с
утверждением владельца (AGENTS.md, 2.2).

### 1.7. Проверки самих средств

Проверка, которая не замечает порчу, ничего не доказывает (AGENTS.md,
4.7). В `.branch-kit/tools/tests` на каждый вид нарушения и каждый код
выхода есть испорченный вход, и проверки показывают, что он пойман.
Площадку в проверках изображают записанные ответы и поддельная площадка;
к настоящей площадке проверки не обращаются. В каждой проверке, где
есть ключ, сверяется, что он не попал в вывод. Проверки, которые
выполняют средство в том же процессе, подменяют окружение целиком
(`helpers.patch_env`), чтобы переменные машины, в том числе строчная
`no_proxy` в Linux, не просочились; проверка
`InProcessEnvTest.test_like_linux` изображает окружение, различающее
регистр имён, как в Linux.

## 2. Проверка репозитория: `check_repo.py`

Выполняет проверки из настройки, поле `проверки`, и печатает итог,
который автор приводит в «Чем проверено», а проверяющий сверяет со своим
(AGENTS.md, 2.6, 4.7).

```
python .branch-kit/tools/check_repo.py [<имя проверки> …] [--config-only]
```

1. Без имён выполняются все проверки по порядку; с именами — только
   названные, и итог тогда говорит, что выполнены не все.
2. Команда выполняется из корня клона: в Linux — оболочкой `sh`, в
   Windows — `cmd`. Если у проверки поля `windows` и `linux`, берётся
   поле своей системы. Команда, начинающаяся словом `python`,
   выполняется тем же Python, что и `check_repo.py`.
3. Окружение команды — окружение запуска без `GITLAB_TOKEN` и без
   переменных ключей из настройки: проверкам сборки ключ не нужен.
4. Успех — код выхода из поля `успех` (без поля — 0) и, если задана,
   строка из поля `строка в выводе` — строка вывода команды целиком, без
   пробелов по краям; причина непрошедшей так и говорит: «(строка
   целиком)». Проверка с полем `не дольше` по истечении срока
   прерывается вместе с дочерними процессами и не проходит.
5. По каждой проверке печатается строка: имя, исход, код выхода,
   длительность; у непрошедшей — ещё последние 20 строк её вывода.
   Полный вывод каждой проверки сохраняется в
   `.git/branch-kit/check_repo/<имя>.log` клона, и путь печатается.
6. Последняя строка — итог с вершиной и чистотой рабочей копии, чтобы
   итог нельзя было приписать другому состоянию:

```
проверок 4: прошли 4, не прошли 0; вершина 1a2b3c4d; рабочая копия чистая
```

Если в рабочей копии до проверок или после них есть изменённые
отслеживаемые файлы или новые файлы, которых `.gitignore` не исключает,
вместо «рабочая копия чистая» стоит «В РАБОЧЕЙ КОПИИ ЕСТЬ НЕСОХРАНЁННЫЕ
ИЗМЕНЕНИЯ» и число тех и других отдельно: такой итог готовность не
доказывает.

Вершина снимается до проверок и после них. Сменилась — итог не прошёл и
называет обе вершины: «ВЕРШИНА СМЕНИЛАСЬ ЗА ВРЕМЯ ПРОВЕРОК, ИТОГ НЕ ПРОШЁЛ: до
1a2b3c4d, после 5e6f7a8b», код 1, даже если все проверки прошли.

Код выхода: 0 — все проверки прошли, вершина не менялась; 1 — хоть одна не
прошла или прервана по сроку либо вершина сменилась; 2 — проверки не
выполнены: настройка не сверилась,
проверок нет, команда не запустилась, файл вывода проверки не открылся,
срок `не дольше` больше, чем умеет ждать система, например `.inf`; срок
сверяется до запуска команды. Проверка в этих случаях названа.

## 3. Формат документов: `check_docs.py`

Проверяет документы по настройке, поле `формат документов` (AGENTS.md,
5.2, 5.4). Обычно его запускает `check_repo.py` как одну из проверок.

```
python .branch-kit/tools/check_docs.py [<файл или каталог> …]
```

Без параметров проверяются файлы, которые отслеживает git и которые
совпали с масками поля `файлы`. Маска сравнивается с путём от корня с
учётом регистра букв, как pathspec git (`git ls-files '*.md'`), а не как
строка `.gitignore`: `*`, `?` и `[!x]` совпадают и с косой чертой, `**`
значит то же, что `*`. Что проверяется — по полям настройки:

| Вид в выводе | Поле настройки | Что проверяется |
|---|---|---|
| `кодировка` | `кодировка` | UTF-8 с BOM или без, как задано |
| `концы строк` | `концы строк` | только LF или только CRLF, без смеси |
| `конец файла` | `перевод строки в конце` | в конце файла перевод строки |
| `длина строки` | `длина строки` | строки вне таблиц и блоков кода не длиннее; 0 — не проверяется; только в файлах `.md`. Блок кода — только огороженный, таблица — строки, которые начинаются с вертикальной черты: блок с отступом, примечание HTML и строка таблицы без ведущей черты проверяются как текст |
| `слово` | `слова` | слово по образцу не употребляется; в выводе — чем его заменить; в самой настройке не проверяется: там слова названы, а не употреблены |
| `ссылка` | `ссылки` | относительная ссылка Markdown ведёт на путь, который отслеживает git и который лежит на диске, — файл или каталог с такими файлами, с учётом регистра букв на любой системе; новый файл, который проверяется сам, тоже годится, если его не исключает `.gitignore`; текст ссылки разбирается, как в CommonMark, и у ссылки вокруг картинки проверяются обе цели — картинки и ссылки; адреса и якоря не проверяются |
| `yaml` | `yaml` | файл `.yaml` и блок `yaml` в документе разбираются; дата вне календаря, например `2026-02-30`, не разбирается |
| `блок кода` | — | блок кода закрыт; нарушение — на строке, которая его открыла: незакрытый блок спрятал бы остаток файла от длины и ссылок, а его блок `yaml` всё равно разбирается. Обратные кавычки в сведениях блока не открывают, как в CommonMark: строка «```x``` — пример» — обычный текст; только в файлах `.md` |

Вывод — строка на нарушение `<файл>:<строка>: <вид>: <что не так>`,
последняя — `нарушений N`. Файл другого расширения длину и ссылки не проходит:
перед итогом тогда стоит строка с числом таких файлов и примером, «файлов без
проверки длины строки и ссылок: 1, например notes.txt»; код выхода от неё не
зависит, и `строка в выводе: нарушений 0` работает по-прежнему. Нет поля
`формат документов` — код 2 с причиной «формат документов не задан». Образец
слова, который не
разбирается как регулярное выражение или разбирается не на всех Python
3.8 и новее, — тоже код 2. Ни одного файла для проверки — маска `docs/`
вместо `docs/*.md`, каталог без файлов по маскам — тоже код 2: «проверка
не выполнена», маски и пути названы. Комплект сам приносит файлы `.md`,
поэтому ноль файлов — ошибка настройки или пути; `check_repo.py` такую
проверку прошедшей не считает.

## 4. Опрос: `poll.py`

Ждёт события в очереди роли и завершается на нём, выведя, что
произошло (AGENTS.md, 4.3). Для агента в Cursor это команда в
терминале: разговор ждёт её завершения, разбирает событие и запускает
её снова.

```
python .branch-kit/tools/poll.py --role planner|author|reviewer [--mr <номер>] [--target <ветка>] [--once] [--reset]
```

| Ключ | Что это |
|---|---|
| `--role` | роль: `planner` — постановщик, `author` — автор, `reviewer` — проверяющий; учётная запись ключа сверяется с этой ролью в настройке, с `--target` — с авторами |
| `--mr` | у автора обязательно: номер своего запроса |
| `--target` | только у проверяющего: очередь проверяющего частей — запросы в названную корневую ветку задачи вместо основной (AGENTS.md, 3.7); у постановщика и автора, с основной веткой или пустым именем — отказ с кодом 2. Ветка сверяется при каждом запуске (`repository/branches/<цель>`): её нет — код 2 с именем ветки, иначе опечатка оставила бы очередь пустой навсегда; ветка есть, запросов в неё нет — `событий 0` |
| `--once` | одно обращение без ожидания: вывести события с прошлого раза и завершиться — для сверки вручную |
| `--reset` | забыть запомненное состояние; следующий запуск — как первый |

События по ролям — таблица AGENTS.md, 4.3:

| Роль | Чьи запросы | События |
|---|---|---|
| постановщик | открытые запросы в основную ветку (настройка, `основная ветка`) | новый запрос; новая заметка в открытом запросе; слияние или закрытие запроса; смена цели запроса (п. 6) |
| автор | свой запрос | новая заметка, смена вершины ветки, смена утверждений, слияние или закрытие; у запроса части — в том числе свои заметки и отправки (п. 4) |
| проверяющий | открытые запросы в основную ветку (настройка, `основная ветка`), кроме черновиков | новый запрос; новая заметка в открытом запросе; смена вершины ветки открытого запроса; смена утверждений; снятие и постановка пометки черновика; смена цели запроса (п. 6) |
| проверяющий частей — агент разработчика (`--role reviewer --target <корневая ветка>`) | открытые запросы в корневую ветку задачи, кроме черновиков | те же, что у проверяющего, и свои заметки и отправки (п. 4) |

Очередь постановщика и проверяющего — только запросы в основную ветку:
запрос части в корневую ветку (AGENTS.md, 3.7) в неё не попадает ни
новым запросом, ни заметкой, ни слиянием. Средство берёт у площадки
открытые запросы с целью — основной веткой из настройки или веткой из
`--target`.

Черновик — запрос с признаком площадки `draft` или с «Draft:» в начале
имени — работа автора (AGENTS.md, 3.7, пп. 1, 7): проверяющий, в том
числе проверяющий частей, его не ведёт. Ни сам черновик, ни заметки,
вершина и утверждения в нём событий не дают; снятие пометки — событие
«снята пометка черновика — на проверке», дальше запрос — как любой. С
постановкой пометки показываются заметки, написанные до неё в том же
промежутке, и смена утверждений этого промежутка: при снятии пометки их
уже не показать. Заметка до или после пометки — по системной заметке площадки
о пометке; такой заметки нет — порядок не определить, и заметка показывается:
лишнее дешевле потерянного. Заметка после пометки молчит.
Постановщик и автор видят черновик, как раньше: в нём автор задаёт
вопрос постановщику (AGENTS.md, 1.6).

1. Период обращений к площадке — настройка, `опрос`, `период`;
   `не дольше` больше нуля — через столько минут опрос завершается без
   события с кодом 1, чтобы его подняли снова; если за этот срок не удалось
   ни одно обращение — с кодом 2 (п. 5).
2. Состояние, с которым сравниваются ответы площадки, хранится в клоне,
   вне отслеживаемых файлов:
   `.git/branch-kit/poll/<роль>[-<номер запроса>][-<корневая ветка>].json`,
   у очереди частей каждой корневой ветки — свой файл. Состояние,
   записанное для другой цели или до фильтра по цели, — код 2 с советом
   начать заново ключом `--reset`. Средство
   записывает его после вывода событий: прерванный между выводом и
   записью запуск покажет те же события снова, но не потеряет их.
   Событие, случившееся, пока опрос не был поднят, следующий запуск
   покажет. Файл состояния не записался — например, в Windows его
   держит открытым второй опрос той же роли, — код 2 с путём к файлу.
3. Первый запуск без состояния выводит исходное состояние — открытые
   запросы, их вершины и последние заметки — как событие и завершается
   с кодом 0: роль сверяет очередь вручную (AGENTS.md, 4.3).
4. Своё событием не считается: заметка учётной записи ключа и смена
   вершины ветки на изменение, сохранённое подписью роли из настройки
   (почта того, кто сохранил изменение, совпадает с почтой подписи).
   Чужое изменение — событие, даже если оно уже есть в локальной ветке
   клона: иначе проверяющий, который взял ветку в локальную ветку для
   проверки результата слияния (AGENTS.md, 2.6), пропустил бы отправку
   автора. У проверяющего частей и у автора запроса части своё — тоже
   событие: они могут работать под одной учётной записью автора
   (AGENTS.md, 1.5), и своё от чужого опрос не отличит.
5. Сбой площадки во время ожидания — повтор на следующем периоде; пять
   сбоев подряд — завершение с кодом 2 и причиной. Срок `не дольше` вышел
   раньше пятого сбоя, а все обращения запуска сбойные — тоже код 2: код 1
   скрывал бы молчащую площадку при каждом новом запуске. Хоть одно обращение
   удалось — код 1.
6. Запрос, пропавший из списка открытых, постановщик и проверяющий
   перечитывают по номеру: открыт с другой целью — событие «цель сменена» у
   обоих, один раз; дальше опрос его не ведёт, цель вернут — придёт новым
   запросом. Открыт с той же целью — остаётся в очереди без события. Слит или
   закрыт — у постановщика событие, у проверяющего молча. Площадка отвечает
   404 — у постановщика событие «удалён», у проверяющего молча; дальше опрос
   его не ведёт. Обращение по номеру — только на пропавший запрос.
7. Заметка, пришедшая между чтением двух страниц заметок, — одно
   событие, а не два.

Вывод — строка на событие и итог:

```
[14:05:12] !12 заметка 3456 от ai-reviewer: Модель проверяющего: …
[14:05:12] !12 вершина ветки 1a2b3c4d → 5e6f7a8b
[14:05:12] !12 утверждения: добавил root
[14:05:12] !13 новый запрос «…» от ai-dev, ветка fix/login-timeout
[14:05:12] !15 цель сменена: main → feat/other — вне очереди
событий 5
```

Код выхода: 0 — есть события (в том числе исходное состояние); 1 —
событий нет: срок `не дольше` вышел, и хоть одно обращение за срок удалось,
или `--once` ничего не нашёл; 2 — опрос не выполнен: настройка, ключ, чужая
учётная запись, ветки из `--target` нет, площадка не отвечает — пять сбоев
подряд или ни одного удавшегося обращения за срок, испорченное состояние, в
том числе запись запроса не того вида, необработанный сбой — как в 1.5.
Ctrl+C — код 130, состояние не меняется.

Как агент Cursor держит опрос и что делать, если команду потеряли или
агента остановили, — в инструкции [cursor-setup.md](cursor-setup.md),
раздел 7. Пробой в Cursor (Windows 11, Cursor 3.23.12) проверено:
команду со сроком `не дольше` 10 минут Cursor держит до конца, и опрос
завершается сам с кодом 1; на заметку опрос ответил событием через 84
секунды при периоде 2. Срок 20 минут Cursor 3.24.12 держал до конца в
Ubuntu 22.04 (19.10.2026, режим Auto-Review (with Sandbox)); в Windows 11
и на Fedora 36 срок больше 10 минут не проверен. Cursor может потерять
запущенную команду — она работает до своего срока, — а после нескольких
пустых опросов подряд останавливает агента как повторяющийся цикл; срок
поэтому нужен и для того, чтобы потерянный опрос завершился сам.

## 5. Журнал слияний: `check_merge_log.py`

Проверяет, что основная ветка менялась только по правилам раздела 2 и
3 AGENTS.md. Читает через API площадки первую линию основной ветки,
слитые запросы, их утверждения и заметки.

```
python .branch-kit/tools/check_merge_log.py
```

| Вид | Что проверяется |
|---|---|
| `не слиянием` | каждое изменение первой линии основной ветки пришло слиянием запроса (AGENTS.md, 3.1) |
| `склейка` | запрос слит способом merge, без склейки (2.4): нет изменения склейки и не включён флаг склейки |
| `сливший автор` | запрос слил не его автор (1.3) |
| `нет варианта решений` | в разделе «Решения» описания ровно один вариант шаблона (2.3) |
| `нет утверждения владельца` | запрос «несёт новое решение» утверждён владельцем (2.2) |
| `нет прямого следа` | у запроса «исполняет решение владельца» есть утверждение владельца, его заметка в запросе или ссылка на запрос с ними (2.5) |
| `повторная ветка` | ветку запроса не использовал другой, уже слитый запрос (3.5) |
| `нет на первой линии` | изменение слияния каждого слитого запроса (поле `merge_commit_sha`) лежит на первой линии: иначе историю основной ветки перезаписали — заменили или откатили (3.4); запрос с пустым полем так не сверить, это не нарушение |

1. Владелец — настройка, `учётные записи`, `владелец`.
2. Ссылка на запрос засчитывается следом, только если узнаётся
   однозначно: `!5` — запрос этого репозитория; `<группа>/<репозиторий>!5`
   и адрес запроса на этой площадке — названного репозитория своей
   группы; адрес без схемы, который начинается своей группой, — путь, а
   не узел, даже если в имени группы есть точка. Неоднозначная ссылка,
   ссылка на другую площадку или в другую группу, адрес, узел которого
   не разбирается, ссылка в блоке кода следом не считаются: ложное «нет
   прямого следа» разбирают исключением, а ложный след прошёл бы молча.
3. Начальное изменение, которое площадка создаёт при заведении проекта,
   не проверяется.
4. Уже слитое нарушение разбирают исключением (1.6): историю основной
   ветки не переписывают (AGENTS.md, 3.4).
5. Раздел «Решения» узнаётся и по заголовку с двоеточием или с
   закрывающими «#»: `## Решения:`, `## Решения ##`. Комментарии HTML и блоки
   кода не читаются; начало комментария в строчном коде — в обратных кавычках
   в пределах одной строки — комментарий не открывает. Настоящий комментарий
   скрыт, и с заголовком «Решения» внутри.

Средство только читает. Коды выхода — по 1.5.

## 6. Защита веток: `owner_protect_branches.py`

**Запускает только владелец** своим ключом: настройки проекта меняет
только он (AGENTS.md, 3.4).

```
python .branch-kit/tools/owner_protect_branches.py [--dry-run] [--host <адрес>] [--config <файл>]
```

1. По каждому префиксу из настройки, поле `ветки задач`, ставит правило
   защиты `<префикс>*`: отправка и слияние — Developer и Maintainer,
   принудительная отправка запрещена.
2. Правило, которое уже есть, не меняет: совпадает с нужным — «без
   изменений», отличается — расхождение, которое владелец правит сам.
   Повторный запуск поэтому ничего не меняет.
3. Основную ветку и настройки слияния только сверяет и не меняет:
   основная ветка — отправка «No one», слияние «Maintainers»,
   принудительная отправка запрещена; способ слияния — merge commit;
   склейка запрещена — `never`, «Do not allow»; ветка после слияния по
   умолчанию не удаляется. Несовпадение — расхождение, в том числе
   склейка `default_off`: она не включена по умолчанию, но разрешена.
   Другое правило, маска которого подходит к основной ветке, — тоже
   расхождение: из подходящих правил GitLab берёт самое мягкое. Поле
   настройки слияния, которого нет в ответе площадки, — расхождение:
   «как нужно» тогда не доказано.
4. По каждому правилу печатает «было — стало»; «стало» — то, что
   ответила площадка, а не то, что средство просило.
5. Учётная запись ключа — не владелец по настройке — отказ с кодом 2.
6. `--dry-run` только показывает, что было бы сделано; код выхода при
   нём 1, если хоть одно правило ещё нужно создать.

Код выхода: 0 — все правила и настройки такие, как нужно; 1 —
расхождение; 2 — не выполнено; 130 — прервано сочетанием Ctrl+C:
правила, о которых строк ещё нет, не ставились.

## 7. Проверка настройки попыткой: `owner_check_settings.py`

**Запускает только владелец.** Попытка делается ключом той учётной
записи, чьи права проверяются; чужим ключом работает только владелец и
только для этого (AGENTS.md, 6.6). Средство ничего не настраивает и не
удаляет; ключ владельца ему не нужен.

```
python .branch-kit/tools/owner_check_settings.py --developer-key <файл> [--maintainer-key <файл>] [--planner-key <файл>] [--host <адрес>] [--config <файл>]
```

| Ключ | Что это |
|---|---|
| `--developer-key` | обязательно: файл ключа учётной записи автора (Developer) |
| `--maintainer-key` | необязательно: файл ключа проверяющего (Maintainer); без него попытка б) — «не проверялось» |
| `--planner-key` | необязательно: файл ключа постановщика (Reporter); без него попытки е) и ж) — «не проверялось» |

Ключи — только из файлов; края файла отбрасываются, как у
`GITLAB_TOKEN` (1.4).

До первой отправки средство сверяет, иначе запуск не выполняется
(код 2): учётные записи ключей — те, что в настройке для своих ролей, и
их роли в проекте — ровно Developer, Maintainer и Reporter, не
администраторы; один ключ не подан на две роли; адрес площадки не
переписан настройкой git `url.*.insteadOf` и не содержит учётных данных;
есть подпись пробных изменений — `user.name` и `user.email` из настроек
git клона, без неё — код 2 «нет подписи для пробных изменений».

| Попытка | Ключ | Ожидаемый исход | Отказ засчитан, если в ответе площадки |
|---|---|---|---|
| а) отправка в основную ветку | автора | отказ | `not allowed to push code to protected branches` |
| б) принудительная отправка в основную ветку | проверяющего | отказ | `not allowed to force push code to a protected branch` |
| в) отправка пробной ветки `test/settings-check-<дата>[-N]` | автора | проходит | — |
| г) принудительная отправка в пробную ветку | автора | отказ | `not allowed to force push code to a protected branch` |
| д) удаление пробной ветки | автора | отказ | `not allowed to delete protected branches` |
| е) отправка в пробную ветку | постановщика | отказ | `not allowed to push code` |
| ж) заметка в запросе из пробной ветки | постановщика | проходит | — |
| з) слияние запроса из пробной ветки | автора | отказ; затем запрос закрывается, не удаляется | код ответа API 401 или 403 |

1. Пробная ветка берёт префикс `test/`; если его нет в настройке, поле
   `ветки задач`, — первый префикс оттуда. Ветка остаётся на площадке:
   ветки не удаляют (AGENTS.md, 3.4); занято имя с датой — добавляется
   `-2`, `-3` и дальше.
2. Перед каждой попыткой средство снимает свежую копию ветки во
   временный каталог. Принудительная отправка и удаление идут с
   `--force-with-lease` на вершину копии: чужое изменение, легшее между
   копией и попыткой, не затирается. Обычную отправку а) и е) в ушедшую
   ветку git отклоняет сам, до площадки, строкой
   `! [rejected] … (fetch first)` или `(non-fast-forward)`. Исход в
   обоих случаях — «НЕ ВЫПОЛНЕНА — ветка ушла с вершины копии»: попытка
   настройку не проверила, это расхождение, и запуск повторяют.
3. Отказ засчитывается, только если ответ площадки называет защиту или
   права, — последний столбец таблицы. Отказ другим ответом настройку не
   подтверждает: «ОТКАЗ НЕ ТЕМ ОТВЕТОМ — НЕ КАК ОЖИДАЛОСЬ».
4. Прошла попытка переписать ветку или удалить её — ветка возвращается
   на вершину копии тем же ключом, с `--force-with-lease` на изменение
   попытки, а после удаления — на отсутствие ветки. Возврат не вышел, а
   на ветке по-прежнему изменение попытки, — средство печатает команду
   возврата для Linux и Git Bash и для PowerShell в форме AGENTS.md,
   6.4: с пустой записью и своим помощником, который читает файл ключа,
   и с запретом переадресации; ключ для неё — свой ключ владельца:
   чужим ключом вне средства не работают (AGENTS.md, 6.6), а права
   владельца не ниже прав роли, чью попытку пропустила защита. Ветка
   после попытки ушла дальше — команды нет: ветку восстанавливают из
   копии вручную. Прошла обычная отправка или слияние — не
   откатывается: ветка называется строкой «ВЕТКА … ОСТАЛАСЬ ИЗМЕНЕНА» с
   вершиной и советом. Основной ветки совет — отменить изменение новым
   запросом; пробной ветки после е) — оставить изменение: пробную ветку
   не сливают; в обоих случаях — исправить настройку. В такую ветку
   запуск больше не пишет.
5. Сбой или Ctrl+C после первой отправки копию не удаляет: печатаются
   «ЗАПУСК ПРЕРВАН ПОСЛЕ ОТПРАВОК», вершины веток до попыток и путь к
   копии.
6. Пробные изменения пустые и подписаны тем, кто запускает; каждая
   отправка идёт с `-o ci.skip`, чтобы не запускать конвейер. Кроме
   попыток и возврата после них, ключом автора средство читает вершины
   веток, снимает копии, читает правила защиты для фрагмента протокола,
   создаёт пробный запрос и закрывает его. Ключи git
   получает помощником учётных данных из переменной окружения своего
   процесса, перед помощником — пустая запись (AGENTS.md, 6.4); из
   окружения не берутся трассировка git (`GIT_TRACE…`,
   `GIT_CURL_VERBOSE`), `GIT_CONFIG_…`, `GIT_DIR` и подобные;
   заголовки `http.extraHeader` сбрасываются. По переадресации git не
   идёт (`http.followRedirects=false`): помощник отдал бы ключ роли
   другому узлу; ответ переадресацией — отказ.

Вывод — строка на попытку и дословный ответ площадки; после попыток —
ветки, оставшиеся изменёнными, итог и фрагмент протокола в YAML:
правила защиты, вершина основной ветки, время, пробная ветка, попытки и
их исходы, итог. Поля «кто» и «подтверждено» владелец дописывает сам.
Протокол вносят в репозиторий запросом в
`.branch-kit/protocols/<дата>-<номер>.yaml`.

Код выхода: 0 — все попытки как ожидалось («не проверялось» без
необязательного ключа расхождением не считается); 1 — расхождение, в
том числе попытка, не выполненная из-за ушедшей ветки, или запуск
прерван после первой отправки, в том числе сочетанием Ctrl+C; 2 —
запуск не выполнен до попыток, в том числе прерван до первой отправки.
Кода 130 у средства нет (1.5).

Чего средство не проверяет: права учётных записей, ключей которых нет в
запуске, в том числе людей; защиту веток задач, кроме пробной, — их
правила видны во фрагменте протокола; удаление ветки запросом API;
слияние без утверждения владельца — бесплатная редакция GitLab его не
останавливает, это держат проверяющий и `check_merge_log.py`.

## 8. Что не проверено

Описание опирается на средства комплекта, из которого взят этот, и на
общее знание о GitLab. На площадке составителей комплекта — GitLab
17.11.2, бесплатная редакция — средство `owner_check_settings.py`
проверено попыткой ([протокол](../protocols/2026-10-10-2.yaml)): защита
веток задач по маске вида `docs/*` не дала Developer принудительно
отправить в пробную ветку и удалить её; Reporter написал заметку в
запросе, а его отправку площадка отклонила строкой «You are not allowed
to push code to this project.»; слияние запроса ключом без права
слияния отклонено кодом 401; настройки площадки ключам ролей не видны —
ответ 403. Не проверены: другие редакции и версии GitLab и их ответы
API, служебные учётные записи агентов, исполнители конвейеров. Средства
