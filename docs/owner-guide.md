# Комплект веточной разработки: инструкция владельцу репозитория

Читатель — владелец репозитория (программный архитектор), который ставит
комплект в свой репозиторий и дальше ведёт по нему работу. Ссылки вида
«AGENTS.md, 4.3» ведут на правила комплекта: здесь это
[kit/AGENTS.md](../kit/AGENTS.md), в вашем репозитории после постановки —
`AGENTS.md` в корне. Настройка — здесь
[kit/.branch-kit/config.yaml](../kit/.branch-kit/config.yaml), в вашем
репозитории — `.branch-kit/config.yaml`.

## 1. Что такое комплект

Комплект — правила, настройка, заготовки и средства, по которым в
репозитории работают ИИ-агенты в Cursor под вашим управлением. Он
держит четыре свойства:

1. Любое изменение идёт через свою ветку и запрос на слияние; в основную
   ветку напрямую не пишет никто (AGENTS.md, 3.1).
2. Каждый запрос проверяет другой агент, по силе модели не слабее автора,
   на результате слияния со свежей основной веткой (AGENTS.md, 1.4,
   2.6).
3. Новое решение сливается только после вашего утверждения (Approve) в
   самом запросе; пересказ вашего решения агентом решением не считается
   (AGENTS.md, 2.2, 2.5).
4. История не теряется: ни принудительной отправки, ни удаления веток, ни
   переписывания отправленного (AGENTS.md, 3.4).

Роли:

| Роль | Кто | Что делает | Модель | Роль на площадке |
|---|---|---|---|---|
| владелец | вы | ставите задачи постановщику, утверждаете новые решения, разбираете споры, меняете настройки площадки, выбираете модели | — | Owner или Maintainer |
| постановщик | агент | разрезает работу на задачи, пишет рабочие задания, следит за запросами | уровня A или замена (AGENTS.md, 1.7) | Reporter |
| автор | агент; их может быть несколько | выполняет задание в ветке, подаёт запрос, отвечает на замечания | по уровню задачи | Developer |
| проверяющий | агент | проверяет запросы, пишет замечания, сливает | уровня A или замена (AGENTS.md, 1.7) | Maintainer |
| проверяющий частей | агент разработчика, когда тот ведёт задачу с частями (AGENTS.md, 3.7) | проверяет запросы частей в корневую ветку, пишет замечания и сводку; не сливает | не слабее модели автора части | учётная запись автора — Developer |
| люди | аналитики, разработчики | ставят задачи агенту-автору и пишут заметки в запросах; разработчик сливает части своей задачи (AGENTS.md, 3.7) | — | Developer или Reporter |

Агенты не обмениваются сигналами: каждая роль работает в своём
разговоре Cursor, а всё, что нужно другой роли, пишет заметкой в
запросе. За своей очередью каждая роль следит сама опросом площадки
(AGENTS.md, 1.8, 4.3).

Что лежит в комплекте:

| Путь в комплекте | Куда попадает | Что это |
|---|---|---|
| `kit/AGENTS.md` | `AGENTS.md` | правила: разделы 1–7 — общая часть, раздел 8 — ваш репозиторий |
| `kit/.cursor/rules/branch-kit.mdc` | `.cursor/rules/branch-kit.mdc` | напоминание агенту Cursor прочитать правила |
| `kit/.gitlab/merge_request_templates/default.md` | `.gitlab/merge_request_templates/default.md` | шаблон описания запроса |
| `kit/.branch-kit/` | `.branch-kit/` | настройка, заготовки, реестр отложенного, средства, исключения, протоколы проверки настройки попыткой |
| `docs/` | не копируется | эта инструкция, задание агенту, тексты запуска проверяющего, постановщика и проверяющего частей, описание средств, настройка Cursor |

## 2. Что завести на площадке

### 2.1. Учётные записи

Агентам нужны свои учётные записи площадки, по одной на роль; людям —
свои. Имена ниже — пример, настоящие записывают в настройку, поле
`учётные записи`.

| Роль | Пример имени | Роль в проекте | Подпись изменений |
|---|---|---|---|
| постановщик | `ai-planner` | Reporter: чтение и заметки | не нужна |
| автор | `ai-dev` | Developer | имя и адрес почты, например `AI Developer` |
| проверяющий | `ai-reviewer` | Maintainer: слияние в основную ветку | имя и адрес почты |
| вы | своя учётная запись | Owner или Maintainer | — |

Учётную запись агента не дают человеку, а свою — агенту: по учётной
записи в истории видно, кто сделал работу (AGENTS.md, 6.6). Агент-автор,
работающий по заданиям людей, пишет под той же учётной записью автора;
люди пишут заметки своими (AGENTS.md, 1.5).

Агент, который ставит или обновляет комплект, берёт его файлы из своего
клона репозитория комплекта (`docs/adaptation-task.md`, ПРОЦЕСС, п. 2).
Поэтому учётной записи автора нужно чтение репозитория комплекта —
участие в нём с ролью Reporter. Если репозиторий комплекта на другой
площадке или доступ дать нельзя, заведите клон комплекта на машине
агента сами и назовите его путь в задании (ДАНО): агент сделает из него
свой клон без ключа.

Что постановщик с ролью Reporter может писать заметки в запросах,
подтверждает таблица прав в документации GitLab: у Reporter есть право
«Leave comments». Что он может писать заметки и не может отправить
изменение, проверено на площадке составителей (GitLab 17.11.2); на
вашей — попыткой (2.5).

### 2.2. Ключи и где их хранить

Каждому агенту — ключ доступа своей учётной записи (Personal Access
Token) с правами `api` и `write_repository`; постановщику достаточно
`api` и `read_repository`. Ставьте ключу срок действия и запишите, когда
его менять.

1. Ключ агента хранят только в переменной окружения пользователя на
   машине, где работает агент. Имя переменной для каждой роли — в
   настройке, поле `переменная ключа`; в заготовке —
   `BRANCH_KIT_PLANNER_TOKEN`, `BRANCH_KIT_AUTHOR_TOKEN`,
   `BRANCH_KIT_REVIEWER_TOKEN`.
2. Ключ не кладут в файлы репозитория, в адрес репозитория, в диспетчер
   учётных данных, в настройки Cursor и glab и не вставляют в разговор с
   агентом (AGENTS.md, 6.3).
3. Если все три агента работают на одной машине, они видят переменные
   друг друга, и каждый берёт только свою — это держат правила
   (AGENTS.md, 6.6), а не машина. Развести ключи надёжно можно только
   разными пользователями системы или разными машинами.
4. Ваш ключ и ключи для проверки попыткой (2.5) храните в файлах вне
   репозитория, закрытых от других пользователей машины.

Как задать переменную в Windows и Linux, чтобы Cursor её увидел, — в
инструкции по настройке Cursor, [cursor-setup.md](cursor-setup.md),
раздел 3.

### 2.3. Настройки проекта

Настройки проекта меняете только вы (AGENTS.md, 3.4).

1. Слияние — способом merge, без склейки: Settings → Merge requests →
   Merge method — «Merge commit»; Squash commits when merging — «Do not
   allow». Ветку после слияния не удаляют, поэтому «Delete source branch»
   по умолчанию выключено.
2. Основная ветка защищена: Settings → Repository → Protected branches —
   отправка (Allowed to push) — «No one», слияние (Allowed to merge) —
   «Maintainers», принудительная отправка (Allowed to force push)
   выключена.
3. Участники проекта — по таблице 2.1, и никого выше нужного: у
   проверяющего — ровно Maintainer, у автора — ровно Developer.

Площадка — GitLab 14.8 или новее: тогда, по документации GitLab, шаблон
запроса `.gitlab/merge_request_templates/default.md` подставляется в
новый запрос сам, и регистр букв в имени шаблона не важен. На площадке
старее шаблон выбирают в форме нового запроса вручную, из списка
шаблонов.

Бесплатная редакция GitLab не останавливает слияние без утверждения
владельца: это держат проверяющий (AGENTS.md, 2.7, шаг 4) и проверка
журнала слияний `check_merge_log.py`.

### 2.4. Защита веток задач

Ветки задач (`docs/*`, `feat/*` и другие префиксы из настройки, поле
`ветки задач`) защищают от принудительной отправки и удаления, оставляя
отправку и слияние Developer и Maintainer. Ставит защиту средство
`.branch-kit/tools/owner_protect_branches.py` вашим ключом, после того
как запрос с комплектом слит и префиксы есть в основной ветке. Средство
печатает по каждому правилу «было — стало» и не трогает правила, которые
уже есть. Как его запустить — `.branch-kit/tools/README.md`.

Разработчик может вести задачу корневой веткой с частями (AGENTS.md,
3.7): части — ветки от корневой ветки с тем же префиксом, их запросы —
в корневую ветку, ревью части ведёт агент разработчика, а сливает часть
сам разработчик своей учётной записью. Защита веток задач уже позволяет
ему сливать в них: правило `<префикс>*` даёт слияние Developer, и под
него попадают и корневая ветка, и части. Для этого у разработчика в
проекте роль Developer, а не Reporter. Постановщик и проверяющий
запросы частей не ведут. Итоговый запрос разработчик подаёт черновиком
«Draft:» сразу после создания корневой ветки и снимает пометку, когда
запросы частей слиты или закрыты: черновик проверяющий не берёт. Текст
запуска агента, который проверяет части, —
[role-start.md](role-start.md), раздел 4.

### 2.5. Проверка настройки попыткой и протокол

Настройку не считают поставленной, пока она не проверена попыткой:
средство `.branch-kit/tools/owner_check_settings.py` пробует запрещённое
и разрешённое ключами самих ролей и сверяет ответ площадки. Это
единственный случай, когда вы работаете чужим ключом (AGENTS.md, 6.6).

| Попытка | Чьим ключом | Ожидается |
|---|---|---|
| отправка в основную ветку | автора | отказ |
| принудительная отправка в основную ветку | проверяющего | отказ |
| отправка пробной ветки `test/settings-check-<дата>` | автора | проходит |
| принудительная отправка и удаление пробной ветки | автора | отказ |
| слияние запроса из пробной ветки | автора | отказ |
| отправка в пробную ветку | постановщика | отказ |
| заметка в запросе из пробной ветки | постановщика | проходит |

Средство печатает исход каждой попытки с дословным ответом площадки и
готовый фрагмент протокола. Протокол вносят в репозиторий, в
`.branch-kit/protocols/`, обычным запросом: отдайте вывод постановщику,
он выдаст задание автору. Попытку повторяют после каждого изменения
настроек проекта и участников.

## 3. Как поставить комплект

1. Заведите на площадке то, что в разделе 2.1–2.3; защиту веток задач
   (2.4) — после шага 7.
2. Подготовьте машину, на которой будут работать агенты, по инструкции
   [cursor-setup.md](cursor-setup.md), разделы 2–6: Cursor, git, glab,
   Python 3.8 или новее с PyYAML, переменные ключей и базы, окно Cursor.
   До первой команды glab с ключом выполните на этой машине один раз,
   без ключа, настройку glab из раздела 4 той же инструкции:
   `glab config set --global telemetry false` и
   `glab config set --global check_update false` — со включённой
   статистикой glab может отправить ключ площадки на `gitlab.com`
   (AGENTS.md, 4.2). Если адрес площадки начинается с `http://`, там же
   выполните `glab config set --host <узел площадки> api_protocol http`:
   без этой настройки glab обращается к площадке по `https`. Ключа в
   этих настройках нет.
3. Выберите изменение комплекта, которое ставите, — первые 8 знаков его
   обозначения в git: оно попадёт в настройку, поле `комплект`. Как
   получить их по метке версии — раздел 5, п. 1.
4. Откройте в Cursor новый разговор на модели уровня A (таблица
   AGENTS.md, 8.4). Нет в вашем Cursor ни одной модели уровня A — на
   замене: самой сильной из доступных моделей ранга 3 уровня B
   (AGENTS.md, 1.7); её же назовите в задании, в ДАНО, и агент впишет
   её в строку замены таблицы 8.4. Передайте агенту задание из
   [adaptation-task.md](adaptation-task.md), заполнив места в угловых
   скобках. Агент работает под учётной записью автора. Файлы комплекта
   он берёт из своего клона комплекта на выбранном изменении (2.1) и
   сам объединяет с уже существующими в репозитории: не копируйте их
   заранее поверх своих.
5. Агент подаёт запрос. Задание дали вы, поэтому вопросы агент задаёт
   вам (AGENTS.md, 1.6): до запроса — в разговоре, после — заметкой в
   запросе. Подав запрос, агент пишет вам в разговор ссылку на него и
   вершину ветки ([adaptation-task.md](adaptation-task.md), ПРОЦЕСС,
   п. 8).
6. Получив ссылку на запрос с комплектом, запустите проверяющего: новый
   разговор в Cursor на модели уровня A (или на замене, шаг 4) и текст
   из [role-start.md](role-start.md), раздел 1, с дополнением
   «Постановка» (там же, раздел 3). Раньше его не запускают: пока
   запроса нет, ветки с комплектом на площадке может не быть, и
   средствам проверяющего, начиная с опроса, взяться неоткуда. В
   основной ветке правил ещё нет, и проверяющий проверяет запрос по
   правилам из его ветки.
7. Запрос несёт новое решение: проверяющий попросит вашего утверждения
   заметкой с упоминанием. Прочитайте раздел 8 `AGENTS.md` и настройку
   в запросе и утвердите (Approve); проверяющий сливает.
8. Поставьте защиту веток задач (2.4), проверьте настройку попыткой
   (2.5) и запустите постановщика: новый разговор на модели уровня A
   (или на замене, шаг 4) и текст из [role-start.md](role-start.md),
   раздел 2.

## 4. Как вести работу

### 4.1. Три агента в Cursor

Постановщик, автор и проверяющий — три отдельных разговора в одном окне
Cursor ([cursor-setup.md](cursor-setup.md), раздел 6), у каждого своя
модель, свой клон и своя переменная ключа.

1. Постановщик и проверяющий работают всё время: у каждого постоянно
   поднят опрос (AGENTS.md, 4.3). Модель у них — самая сильная из
   уровня A, а если моделей уровня A в Cursor нет — замена (AGENTS.md,
   1.7). Запускают их готовыми текстами из [role-start.md](role-start.md).
2. Автора поднимают на задание: новый разговор на модели уровня задачи,
   который заканчивается слиянием или закрытием запроса.
3. Опрос — команда, которая ждёт события и завершается на нём; агент
   разбирает событие и поднимает её снова. Срок, после которого команда
   завершается без события, — в настройке, поле `опрос`, `не дольше`:
   меньше того, через сколько Cursor обрывает долгие команды. Команду со
   сроком 10 минут Cursor держит до конца; со сроком 20 минут её держал
   до конца Cursor 3.24.12 в Ubuntu 22.04 (19.10.2026), на других
   системах дольше 10 минут не проверено.
4. При долгой тишине в очереди Cursor сам останавливает агента как
   повторяющийся цикл — на пробе после четырёх пустых опросов подряд,
   через 34 минуты. Загляните в разговоры постановщика и проверяющего и
   продолжите остановленного новым сообщением: «продолжай: подними
   опрос». Cursor может и потерять запущенную команду опроса; что тогда
   делать, как найти оставшийся опрос и снять его — в
   [cursor-setup.md](cursor-setup.md), раздел 7.
5. После перезапуска Cursor разговоры остаются на месте: попросите
   каждого агента поднять опрос и сверить очередь вручную.

### 4.2. Кто кому что передаёт

| Что | От кого | Кому | Как |
|---|---|---|---|
| цели и задачи | вы | постановщик | разговор постановщика |
| рабочее задание с уровнем и моделями | постановщик | вы | разговор постановщика |
| то же задание | вы | автор | новый разговор на модели нужного уровня; текст — дословно |
| запрос и первая заметка | автор | постановщик, проверяющий | запрос; они видят его опросом |
| вопрос автора по заданию | автор | постановщик | заметка в запросе (до запроса — в черновике «Draft:»); ответ — заметкой постановщика |
| замечания и ответы | проверяющий и автор | друг другу | заметки в запросе (AGENTS.md, 4.6, 4.10) |
| просьба утвердить, спор | проверяющий | вы | заметка с упоминанием вашей учётной записи (AGENTS.md, 2.7, 4.11) |
| ваше решение | вы | всем | Approve или заметка в запросе вашей учётной записью — прямой след (AGENTS.md, 2.5) |
| слияние | проверяющий | постановщик | заметка о слиянии; постановщик видит её опросом |

Сказанное вами агенту в разговоре следом решения не является: решение
записывают утверждением или заметкой в запросе (AGENTS.md, 2.5).
Упоминания площадка присылает в ваш список дел (To-Do) и почтой, если
почта настроена.

### 4.3. Ваши обязанности

1. Утверждать запросы с новым решением, прочитав изменение (AGENTS.md,
   2.2).
2. Разбирать споры и третий круг правок (AGENTS.md, 4.11).
3. Менять настройки проекта и участников и после этого проверять их
   попыткой (2.3–2.5).
4. Выбирать модели для ролей и держать таблицу моделей (4.4).
5. Отвечать на вопросы агентов по заданиям, которые дали сами
   (AGENTS.md, 1.6).
6. Разрешать или не разрешать агенту запуск других исполнителей —
   субагентов, фоновых агентов — на его задачу: разрешаете только вы
   (AGENTS.md, 1.9).

Очередь за агентов вы не ведёте: каждая роль следит за своей сама
(AGENTS.md, 4.11).

### 4.4. Таблица моделей и как её править

Работу дают по уровню задачи — A, B или C, а принимают по рангу модели
(AGENTS.md, 1.7). Какие модели к какому уровню относятся, записано в
таблице AGENTS.md, 8.4. Её заполнили составители комплекта моделями,
которые им известны; если в вашем Cursor другие модели, поправьте её:

1. Дайте постановщику задачу: «таблица 8.4 — такие-то модели по уровням
   и рангам». Правка правил — работа уровня A или замены (AGENTS.md,
   1.7).
2. Автор правит таблицу запросом с новым решением; вы его утверждаете.

Если в вашем Cursor нет ни одной модели уровня A из таблицы, всю работу
уровня A, в том числе постановку задач, проверку запросов и правку
правил, делает замена: самая сильная из доступных моделей ранга 3
уровня B. Её вы называете строкой замены в таблице 8.4 при постановке
комплекта (раздел 3, шаг 4). Не стало моделей уровня A позже — задачей
постановщику, как выше: постановщик, автор и проверяющий этого запроса
уже работают на замене (AGENTS.md, 1.7).

Неизменным остаётся: постановщик и проверяющий — модели уровня A или,
если их в Cursor нет, замена (AGENTS.md, 1.7); проверяющий не слабее
автора по рангу; модель, которой нет в таблице, работы не получает.
Режим Auto в Cursor не используют: модель в нём неизвестна, и её ранг
тоже.

## 5. Как обновлять комплект

1. Посмотрите, что изменилось в комплекте между изменением из поля
   `комплект` вашей настройки и новым, — в своём клоне репозитория
   комплекта. Нет клона — заведите его по AGENTS.md, 6.4: помощник
   учётных данных читает файл вашего ключа (2.2, п. 4), переадресация
   запрещена; подпись для чтения не нужна. Адрес хранилища комплекта —
   `<адрес площадки>/<группа>/<репозиторий>.git` репозитория комплекта,
   с `.git` на конце; путь к файлу ключа пишут через `/` (AGENTS.md,
   6.4).

   ```
   # Linux и Git Bash
   git -c credential.helper= -c credential.helper='!f() { echo username=oauth2; echo "password=$(cat <файл ключа>)"; }; f' clone -c core.autocrlf=false -c http.followRedirects=false <адрес хранилища комплекта> <клон комплекта>
   git -C <клон комплекта> config --local credential.helper ""
   git -C <клон комплекта> config --local --add credential.helper '!f() { echo username=oauth2; echo "password=$(cat <файл ключа>)"; }; f'
   git -C <клон комплекта> config --local http.followRedirects false
   ```

   ```
   # Windows, PowerShell
   git --% -c credential.helper= -c credential.helper="!f() { echo username=oauth2; echo \"password=$(cat <файл ключа>)\"; }; f" clone -c core.autocrlf=false -c http.followRedirects=false <адрес хранилища комплекта> <клон комплекта>
   git -C <клон комплекта> config --local credential.helper --% ""
   git -C <клон комплекта> config --local --add credential.helper --% "!f() { echo username=oauth2; echo \"password=$(cat <файл ключа>)\"; }; f"
   git -C <клон комплекта> config --local http.followRedirects false
   ```

   Версии комплекта отмечены метками вида `v<номер>`; первая — `v1.0`.
   Новое изменение для обновления берут по метке: подтяните в клон
   новые изменения комплекта, посмотрите список меток и сравните, указав
   вместо `<новое>` имя метки:

   ```
   # Обе системы
   git -C <клон комплекта> fetch
   git -C <клон комплекта> tag -l "v*"
   git -C <клон комплекта> log --oneline <старое>..<новое> -- kit/
   ```

   В задание агенту и в поле `комплект` настройки идёт не имя метки, а
   первые 8 знаков обозначения изменения. По метке их печатает команда
   ниже. Добавка `^{commit}` нужна: метка с описанием — отдельный объект
   git, и без добавки команда напечатала бы обозначение самой метки.
   Кавычки нужны для PowerShell: без них он не передаёт фигурные скобки
   git.

   ```
   # Обе системы
   git -C <клон комплекта> rev-parse --short=8 "<метка>^{commit}"
   ```

2. Дайте агенту уровня A (нет моделей уровня A — замене, AGENTS.md,
   1.7) задание из [adaptation-task.md](adaptation-task.md), раздел
   «Обновление»; в ДАНО — новое изменение комплекта. Агент
   заменит общую часть, сохранит ваше, заполнит новые поля и подаст
   запрос с новым решением.
3. Утвердите запрос, как при постановке.

Общую часть в своём репозитории не правят (`.branch-kit/README.md`):
недостаток комплекта называют его составителям, и он исправляется в
новой версии.
