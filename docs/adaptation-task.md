# Задание агенту: поставить комплект в репозиторий

Готовое задание агенту, который ставит комплект веточной разработки в
репозиторий и приспосабливает его к стеку, сборке и тестам этого
репозитория. Задание даёт владелец репозитория (инструкция владельцу,
[owner-guide.md](owner-guide.md), раздел 3); уровень задачи — A.

Как отдать задание:

1. Откройте в Cursor новый разговор на модели уровня A (таблица
   `kit/AGENTS.md`, 8.4). Нет в вашем Cursor ни одной модели уровня A —
   на замене (`kit/AGENTS.md`, 1.7): самой сильной из доступных моделей
   ранга 3 уровня B; её же впишите в ДАНО.
2. Заполните места в угловых скобках в рамке ниже, кроме `<база>`: её
   агент определяет сам. Адрес хранилища пишут, как в `kit/AGENTS.md`,
   6.4: `<адрес площадки>/<группа>/<репозиторий>.git`, с `.git` на
   конце; без него клон агента на площадке остановится.
3. Отправьте агенту текст из рамки целиком. Для обновления уже
   поставленного комплекта к нему добавьте текст из раздела
   «Обновление».

Задание дали вы, поэтому вопросы агент задаёт вам: до запроса — в
разговоре, после — заметкой в запросе (`kit/AGENTS.md`, 1.6). Отвечайте
там же, где спросили; решение по разделу 8 и настройке вы даёте
утверждением запроса.

```
Ты — АВТОР по правилам комплекта веточной разработки, роль — 1.3 его
AGENTS.md. Правил комплекта в репозитории <группа>/<репозиторий> ещё нет:
до слияния этого запроса работаешь по kit/AGENTS.md комплекта, после —
по AGENTS.md репозитория. Задание дал владелец репозитория
<учётная запись владельца>; вопросы задавай ему (kit/AGENTS.md, 1.6).
Уровень задачи — A (kit/AGENTS.md, 1.7, 8.4).

ДАНО
- Комплект: <адрес хранилища комплекта> — у твоей учётной записи
  есть его чтение; либо, если доступа нет, клон комплекта, который завёл
  владелец, — <путь на этой машине>. Изменение комплекта — <8 знаков>.
- Репозиторий: <адрес площадки>/<группа>/<репозиторий>.git, основная
  ветка <main или другое имя>.
- Твоя учётная запись — <учётная запись автора>, ключ — в переменной
  окружения <имя переменной ключа автора>; подпись — имя
  <имя для подписи>, почта <адрес почты>.
- Учётные записи других ролей — <постановщик>, <проверяющий>, люди —
  <учётные записи и роли либо «нет»>.
- Замена уровня A (kit/AGENTS.md, 1.7, 8.4): <«не нужна», если в
  Cursor есть модель уровня A из таблицы 8.4; иначе — имя модели
  замены: самой сильной из доступных моделей ранга 3 уровня B, на
  которой открыт этот разговор>.

ЗАДАЧА
1. Изучи репозиторий запуском, а не по догадке: язык и стек; как он
   собирается; тесты и как их запускать; линтеры и форматтеры; конвейер
   (.gitlab-ci.yml, Jenkinsfile и подобные); принятые имена веток;
   формат документов; существующие правила для людей и агентов —
   AGENTS.md, CONTRIBUTING, .cursor/rules/, .gitlab/ и подобные.
2. Перенеси содержимое каталога kit/ из клона комплекта (ПРОЦЕСС,
   п. 2) в корень репозитория с теми же путями, без kit/ в начале.
3. Существующее объедини, а не затри:
   - AGENTS.md: разделы 1–7 — из комплекта без изменений; прежние правила
     репозитория перенеси в раздел 8.5 «Свои правила» по смыслу, ничего
     не теряя; правило, которое противоречит разделам 1–7, перенеси как
     есть и назови в «Открытых вопросах» — решает владелец;
   - .gitlab/merge_request_templates/: если шаблон по умолчанию уже есть
     (имя default.md в любом регистре букв), шаблоном по умолчанию
     становится шаблон комплекта, а прежние разделы идут между разделом
     «Открытые вопросы» и чертой перед чек-листом; другие шаблоны не
     трогай;
   - .cursor/rules/: прежние файлы не трогай, branch-kit.mdc добавь;
     прежнее правило, которое противоречит AGENTS.md, назови в «Открытых
     вопросах»;
   - другие файлы с правилами для агентов не трогай и назови в «Замечено
     по дороге».
4. Заполни настройку .branch-kit/config.yaml: каждое место в угловых
   скобках — из раздела ДАНО и того, что нашёл в пункте 1. В поле
   «проверки» — команды, которыми репозиторий проверяют перед слиянием:
   сборка, тесты, линтеры, проверка документов. Для Windows и Linux —
   свои команды, если они различаются. Формат документов — тот, что
   принят в репозитории, а не пример комплекта; принятого нет —
   предложи и назови в «Открытых вопросах».
5. Заполни раздел 8 AGENTS.md: 8.1 — что это за репозиторий; 8.2 — что
   где лежит; 8.3 — сборка и проверки; 8.4 — таблицу моделей оставь
   комплекта, если владелец не дал своей; строку замены уровня A
   заполни моделью из ДАНО, а если замена не нужна — удали строку;
   8.5 — свои правила.
6. Для каждой проверки из поля «проверки» докажи, что она падает на
   испорченном входе (kit/AGENTS.md, 4.7): испорти вход — сломай тест,
   внеси нарушение линтера, сломай сборку, удлини строку документа, —
   выполни python .branch-kit/tools/check_repo.py, убедись, что эта
   проверка не прошла и итоговая строка это показывает, верни вход.
   Порчу и ответ проверки запиши в таблицу 8.3. Проверку, которую
   испортить не удалось, в поле «проверки» не ставь и назови в
   «Открытых вопросах».
7. Выполни python .branch-kit/tools/check_repo.py на готовой ветке:
   все проверки проходят.

Рамки: язык — русский; разделы 1–7 AGENTS.md, заготовки
.branch-kit/templates/ и средства .branch-kit/tools/ — как в комплекте;
ключей, паролей, локальных путей и личных данных в файлах нет
(kit/AGENTS.md, 7.2).

ПРОЦЕСС
1. Клон — <база>/clones/<репозиторий>-branch-kit по kit/AGENTS.md, 6.4,
   с помощником из переменной ключа; сверка — 6.2. База — переменная
   окружения BRANCH_KIT_WORK_ROOT; её нет — спроси меня.
2. Клон комплекта — <база>/clones/branch-kit-<8 знаков изменения>. По
   адресу из ДАНО — тем же помощником (kit/AGENTS.md, 6.4), подпись не
   нужна. По пути из ДАНО — git clone -c core.autocrlf=false <путь>
   <клон комплекта>, ключ площадки не нужен. Настройка
   -c core.autocrlf=false после clone попадает в клон до выкладки
   файлов, и они выкладываются как в репозитории, без перевода концов
   строк. Сам клон владельца не открывай и не меняй (6.1). Затем
   git -C <клон комплекта> checkout --detach <изменение из ДАНО> и
   сверка: git -C <клон комплекта> rev-parse HEAD начинается с него.
   Файлы комплекта бери только из этого клона; в нём ничего не меняй и
   не отправляй. Клон не берётся — остановись и спроси меня.
3. Ключ glab — переменной GITLAB_TOKEN на каждую команду, вместе с
   GLAB_SEND_TELEMETRY=false и GLAB_CHECK_UPDATE=false. До первой
   команды с ключом — разовая настройка glab по kit/AGENTS.md, 4.2:
   статистика и проверка обновлений выключены, иначе glab может
   отправить ключ на gitlab.com, а при адресе площадки с http:// —
   api_protocol http. Первой командой — glab api user: в ответе
   <учётная запись автора>.
4. Ветка chore/branch-kit от свежего origin/<основная ветка>.
5. Работа по ЗАДАЧЕ; сообщения к изменениям — «chore: что сделано».
6. Перед подачей — слияние свежей основной ветки в свою и пункт 7
   ЗАДАЧИ на результате.
7. Запрос — через glab, описание файлом по шаблону комплекта. В
   «Решениях» одной строкой: «- несёт новое решение: постановка
   комплекта веточной разработки — раздел 8 AGENTS.md и настройка —
   нужно утверждение владельца». В «Чем проверено» — итоговая строка
   check_repo.py и по каждой проверке — порча и ответ. В «Открытых
   вопросах» — всё, что решил сам сверх задания.
8. Стоп после подачи: не сливать. Ссылку на запрос и вершину ветки
   напиши мне в разговор.
9. Опрос своего запроса до слияния (kit/AGENTS.md, 4.3): на каждое
   замечание — отдельный ответ (4.6), каждая отправка после подачи — с
   заметкой (3.6).
ЗАПРЕЩЕНО: менять разделы 1–7 AGENTS.md, заготовки и средства комплекта
— замеченное в них назови в «Замечено по дороге», это правка самого
комплекта; удалять или переписывать прежние правила репозитория —
только переносить в 8.5; сливать свой запрос — сливает проверяющий после
утверждения владельца; печатать ключ и класть его в файлы.

ИТОГ: ссылка на запрос, вершина ветки, одна строка состояния.
```

## Обновление

Если комплект в репозитории уже стоит и его нужно обновить до нового
изменения, к заданию выше добавьте этот текст. Он заменяет пункты 2–5
ЗАДАЧИ, пункты 1, 6 и 7 остаются; ветка —
`chore/branch-kit-update-<8 знаков нового изменения>`.

```
ОБНОВЛЕНИЕ
Комплект уже стоит: какое изменение — в .branch-kit/config.yaml, поле
«комплект». Новое изменение — то, что в ДАНО; клон комплекта — по
ПРОЦЕССУ, п. 2, в нём есть оба изменения.
1. Сравни kit/ комплекта между стоящим изменением и новым:
   git -C <клон комплекта> diff <стоящее>..<новое> -- kit/
2. Общую часть замени файлами нового изменения целиком: разделы 1–7
   AGENTS.md, .cursor/rules/branch-kit.mdc, шаблон запроса, кроме
   разделов репозитория между «Открытыми вопросами» и чертой перед
   чек-листом, .branch-kit/templates/, .branch-kit/tools/,
   .branch-kit/README.md, .branch-kit/protocols/README.md.
3. Своё сохрани: раздел 8 AGENTS.md, значения настройки, реестр
   отложенного, исключения .branch-kit/exceptions.yaml, протоколы в
   .branch-kit/protocols/, разделы репозитория в шаблоне запроса.
4. Новые поля настройки и новые места раздела 8 заполни по тому, что
   нашёл в пункте 1 ЗАДАЧИ; строку замены уровня A в 8.4 — по ДАНО,
   как в пункте 5 ЗАДАЧИ; в поле «комплект» поставь новое изменение.
5. Если изменились поле «проверки» или средства — пункт 6 ЗАДАЧИ для
   затронутых проверок.
В «Решениях»: «- несёт новое решение: обновление комплекта веточной
разработки до <8 знаков> — нужно утверждение владельца».
```
