# Средства комплекта

Средства, которыми пользуются владелец репозитория, агенты и люди на
своих машинах: проверка репозитория, проверка документов, опрос площадки,
проверка журнала слияний, защита веток и проверка настройки площадки
попыткой. Правила, которые на них ссылаются, — `AGENTS.md`, 3.4, 4.3,
4.7, 5.4 и 6.6.

| Средство | Что делает | Кто запускает |
|---|---|---|
| `check_repo.py` | выполняет проверки из настройки, последней строкой — итог для раздела «Чем проверено» | автор, проверяющий |
| `check_docs.py` | проверяет формат документов по настройке | все, обычно как проверка из настройки |
| `poll.py` | опрос: ждёт события в очереди роли и завершается на нём | постановщик, автор, проверяющий |
| `check_merge_log.py` | проверяет журнал слияний основной ветки | все |
| `owner_protect_branches.py` | ставит защиту веток задач по префиксам из настройки, сверяет защиту основной ветки и настройки слияния | только владелец |
| `owner_check_settings.py` | проверяет настройку площадки попыткой | только владелец |

`kit_common.py` — общая часть средств, сам не запускается; `tests/` —
проверки самих средств (раздел «Проверки самих средств»).

## Что нужно

1. Python 3.8 или новее и PyYAML 5.1 или новее; PyYAML ставится командой
   `python -m pip install pyyaml`. Других зависимостей нет: средства
   пользуются только стандартной библиотекой Python и PyYAML. Проверки
   самих средств (раздел «Проверки самих средств») 20.10.2026 прошли
   все, 215 проверок, в Windows 10 на Python 3.8.10, 3.9.13, 3.10.11,
   3.11.9, 3.12.10, 3.13.16 и 3.14.8 с PyYAML 6.0.1; все версии, кроме
   3.11.9, — встраиваемые сборки с python.org, PyYAML в них — без
   расширения на C; 3.9.13 — последний выпуск 3.9 с такой сборкой.
   Сверка настройки на всех этих версиях даёт один итог (раздел
   «Настройка», п. 5). Протокол ALPN при соединении по https средства
   предлагают тот же, что Python той же версии по умолчанию: на 3.8 и
   3.9 — никакого, с 3.10 — `http/1.1` (замерено на этих версиях с
   поддельной площадкой). В Ubuntu 22.04 на Python 3.10.12 13.10.2026
   прошла 161 проверка из 162: упала проверка русского текста ошибки в
   ключе — argparse Python до 3.11 не переводит в нём слово «argument».
   Теперь средства собирают эту строку сами; 19.10.2026 в Ubuntu 22.04
   на Python 3.10.12 (Python дистрибутива) на изменении комплекта
   `071a1cdf` из 211 проверок прошли 209, две пропущены — они только
   для Windows (`test_cmd_output_in_oem`, `test_file_held`).
   20.10.2026 на Fedora 36 на Python 3.8.20, 3.9.20 (переносимые сборки
   python-build-standalone) и 3.10.11 (Python дистрибутива) с PyYAML
   6.0.1 без расширения на C на изменении комплекта `be7c2163`, с
   переменными `no_proxy` и `NO_PROXY` машины (в них — узел площадки), из
   215 проверок прошли 213, те же две пропущены. До исправления проверок,
   на `288d381e`, со снятыми переменными было 211 из 213, а с ними — 16
   падений: изъян проверок, а не средств.
2. git 2.x: средства берут у git корень клона, его каталог git, перечень
   файлов и вершину, а `owner_check_settings.py` делает им попытки.
   Проверено на git 2.40.0 в Windows 10, на git 2.34.1 в Ubuntu 22.04
   (13.10.2026, та же машина, что в п. 1) и на git 2.40.1 на Fedora 36
   (20.10.2026, та же машина, что в п. 1).
3. Для `poll.py`, `check_merge_log.py` и владельческих средств — доступ
   к площадке и ключ (раздел «Ключ и площадка»).

## Как запускать

Средство запускают из корня клона. В правилах и ниже команда записана с
`python`; в Linux вместо неё пишут `python3`, в Windows, если `python`
не находится, — `py -3` (AGENTS.md, вводная часть перед разделом 1).

```
python .branch-kit/tools/check_repo.py
```

Клон и настройку средство находит по своему месту, а не по текущему
каталогу: корень клона — корень рабочей копии git, в которой лежит
каталог средств, настройка — `.branch-kit/config.yaml` рядом с ним. Так
средство, настройка и клон всегда из одной рабочей копии; переменные
окружения `GIT_DIR`, `GIT_WORK_TREE` и подобные клон не подменяют.

Вывод — в UTF-8 на любой системе. Если в Windows PowerShell 5.1
кириллица в выводе неразборчива, перед запуском выполните:

```
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
```

## Настройка

Каждое средство читает `.branch-kit/config.yaml`; ключ `--config <файл>`
задаёт другой файл. До любого действия средство сверяет настройку и при
нарушении завершается с кодом 2, назвав строку и поле:

```
.branch-kit/config.yaml:25: поле «площадка / адрес»: осталось место «<адрес площадки>» — заполните
настройка не сверилась: нарушений 1
```

Что сверяется:

1. Файл разбирается безопасным загрузчиком YAML; обязательные поля есть
   и нужного вида: строка, число, целое число, список, запись с полями,
   `true` или `false`. Строка не пустая; список веток задач, авторов и
   масок файлов — тоже.
2. В значениях не осталось места вида `<…>`: незаполненная настройка не
   годится ни для одного средства. Перенаправление в команде проверки,
   например `sort <in.txt >out.txt`, местом не считается; в образце
   слова не считаются местом и знаки регулярного выражения: имя группы
   в `(?P<имя>…)` и начало `(?<=…)` и `(?<!…)`. Текст `<…>` в образце —
   место, как в любом поле.
3. Неизвестное или повторённое поле — нарушение: опечатка в имени поля
   иначе молча выключила бы его.
4. Значения: адрес площадки — целиком, с `http://` или `https://`, без
   учётных данных; репозиторий — `<группа>/<имя>` с группой из поля
   `группа`; имена переменных окружения — латиница, цифры и `_`; имя
   проверки — латиницей и без повторов; у проверки — `команда` либо оба
   поля `windows` и `linux`; срок проверки и период опроса — больше нуля,
   `не дольше` опроса — 0 или больше; кодировка, концы строк и роль
   человека — из подсказки над полем; образец слова разбирается как
   регулярное выражение.
5. Адрес площадки и образец слова сверяются одинаково на всех Python 3.8
   и новее: то, что разные версии разбирают по-разному, — нарушение на
   любой из них. В адресе пробелы по краям отбрасываются, а пробел или
   управляющий знак внутри — нарушение; квадратные скобки — только парой
   вокруг адреса IPv6, например `http://[::1]:8080`. Образец — без того,
   что есть только в новых Python: атомарной группы `(?>…)`, повторов
   `*+`, `++`, `?+`, `{m,n}+` и `\z`; флаги вида `(?i)` — только в
   самом начале образца; в условии `(?(…)…)` — имя группы или её номер
   цифрами 0–9.

Сверку настройки отдельно, без другой работы, выполняет
`python .branch-kit/tools/check_repo.py --config-only`.

## Ключ и площадка

Ключ нужен `poll.py`, `check_merge_log.py` и
`owner_protect_branches.py`. Его подают переменной `GITLAB_TOKEN` на
одну команду; `<ПЕРЕМЕННАЯ>` — переменная ключа своей роли из настройки,
поле `учётные записи` (AGENTS.md, 6.3), у владельца — переменная или
файл с его ключом:

```
# Linux и Git Bash
GITLAB_TOKEN="$<ПЕРЕМЕННАЯ>" python .branch-kit/tools/poll.py --role reviewer
# Windows, PowerShell
try { $env:GITLAB_TOKEN = $env:<ПЕРЕМЕННАЯ>; python .branch-kit/tools/poll.py --role reviewer } finally { Remove-Item Env:GITLAB_TOKEN -ErrorAction SilentlyContinue }
```

`owner_check_settings.py` ключей из переменных не берёт: ключи ролей ему
подают файлами (раздел о нём).

1. Ключ не печатается ни в выводе, ни в сообщениях об ошибке, ни в
   адресе запроса.
2. Ключ — только печатные знаки ASCII без пробелов. Пробелы, перевод
   строки и возврат каретки по краям отбрасываются: файл ключа с концами
   строк CRLF, поданный через `$(cat …)`, оставляет в переменной `\r`, и
   ключ всё равно годен. Ключ с другими знаками или с меткой порядка
   байтов (файл, записанный PowerShell 5.1 с `-Encoding utf8`) — отказ с
   кодом 2 до первого обращения к площадке: «в GITLAB_TOKEN не ключ».
   Метку причина называет отдельно: «в начале — метка порядка байтов
   (BOM)». Средства её не отбрасывают: с ней ключ не примут ни glab, ни
   git, и поправить нужно сам файл ключа.
3. Площадка — поле `площадка`, `адрес`; ключ `--host <адрес>` задаёт
   другую. glab средствам не нужен: к площадке они обращаются сами.
4. Средство, которое действует за роль, — `poll.py` и владельческие —
   первым обращением узнаёт учётную запись ключа и сверяет её с ролью в
   настройке: чужая учётная запись — отказ с кодом 2 (AGENTS.md, 6.6).
   Проверяющий частей — агент разработчика под учётной записью автора
   (AGENTS.md, 1.5, 3.7): у `poll.py --role reviewer --target` ключ —
   учётной записи одного из авторов, ключ проверяющего — отказ.
   `check_merge_log.py` только читает и годится с ключом любой учётной
   записи, которая видит проект.
5. Прокси средства берут только из переменных окружения, как glab:
   `HTTP_PROXY`, `HTTPS_PROXY` и те же имена строчными буквами.
   Системный прокси — настройки прокси Windows в реестре, настройки
   рабочего стола в Linux — средства не читают ни на одной системе, в
   том числе когда переменных нет: urllib без этого в Windows взял бы
   прокси из реестра. Узел площадки, названный в `NO_PROXY`, идёт мимо
   прокси. Записи — как у glab: имя узла — он сам и имена, которые им
   оканчиваются, в том числе с точкой или `*.` в начале; адрес; сеть
   вида `10.0.0.0/8`; `*` — любой узел. У записи, кроме сети, может
   стоять порт — `узел:порт`, у адреса IPv6 `[адрес]:порт`, и тогда она
   действует только для этого порта; порт площадки, не названный в
   адресе, — 80 у `http://` и 443 у `https://`.
6. Переадресацию площадки средства не выполняют: urllib перенёс бы ключ
   на новый адрес, в том числе на другой узел, а ответ чужого узла
   средство приняло бы за ответ площадки. Ответ переадресацией — отказ с
   кодом 2; в причине — куда она вела: адрес площадки в настройке тогда
   поправляют.
7. Ключи шифрования TLS средства в файл не пишут. Python по умолчанию
   пишет их в файл, названный переменной окружения `SSLKEYLOGFILE`, а по
   ним расшифровывается запрос по https вместе с ключом площадки; с
   Python 3.12 файл появляется уже при сборке клиента, в том числе при
   площадке по http. Контекст TLS у средств свой: переменную он не
   читает, а сертификат и имя узла сверяет так же, как Python той же
   версии по умолчанию.
8. На машине агента постоянной переменной `SSLKEYLOGFILE` нет: её
   читают и другие программы, через которые агент ходит к площадке. git
   ходит по https через библиотеку libcurl, а она, по документации curl,
   пишет ключи, когда работает на OpenSSL или GnuTLS; GnuTLS, по своей
   документации, пишет их и сама, в любой программе. Замерено в Windows
   10: git 2.40.0 с `http.sslBackend=openssl` ключи записал, с
   `schannel` — нет; glab 1.110.0 и 1.123.0 переменную не читают. В Linux git
   собран с libcurl на GnuTLS (Ubuntu) или OpenSSL (Fedora); там не
   проверено. Видит ли переменную терминал агента, не печатая значения,
   показывают команды ниже; ожидается «нет». Задана постоянно — её
   снимают: в Windows — для пользователя и для машины, в Linux — из
   файлов входа и `~/.config/environment.d/`.

```
# Linux и Git Bash
test -n "$SSLKEYLOGFILE" && echo 'SSLKEYLOGFILE задана' || echo 'SSLKEYLOGFILE нет'
# Windows, PowerShell
if ($env:SSLKEYLOGFILE) { 'SSLKEYLOGFILE задана' } else { 'SSLKEYLOGFILE нет' }
```

заголовок `X-Next-Page`. Заголовок есть и пуст — конец выдачи, в том числе
при полной странице: так GitLab отвечает на ровно полную последнюю
страницу запросов. Заголовка нет при неполной странице — тоже конец. Сбой
площадки, с той же обработкой, что и отсутствие ответа: заголовка нет вовсе
при полной странице — прокси мог срезать его, и выдача молча оборвалась бы
на сотне записей; номер следующей страницы не больше текущей или не номер —
обход не кончился бы, и срок `не дольше` его не прервал бы.

## Проверка репозитория: `check_repo.py`

```
python .branch-kit/tools/check_repo.py [<имя проверки> …] [--config-only]
```

Выполняет проверки из настройки, поле `проверки`, и печатает итог,
который автор приводит в «Чем проверено», а проверяющий сверяет со своим
(AGENTS.md, 2.6, 4.7).

1. Без имён выполняются все проверки по порядку; с именами — только
   названные, и итог говорит, что выполнены не все.
2. Команда выполняется из корня клона: в Linux — оболочкой `sh`, в
   Windows — `cmd`. Если у проверки поля `windows` и `linux`, берётся
   поле своей системы. Команда, начинающаяся словом `python`,
   выполняется тем же Python, что и `check_repo.py`.
3. Окружение команды — окружение запуска без `GITLAB_TOKEN` и без
   переменных ключей из настройки: проверкам сборки ключ не нужен. Ключ
   `--config` командам не передаётся: `check_docs.py` в проверке читает
   свою настройку по умолчанию.
4. Успех — код выхода из поля `успех`, `код выхода` (без поля — 0) и,
   если задана, строка из поля `строка в выводе`. Строка засчитывается,
   только если она — строка вывода целиком, без пробелов по краям: часть
   строки не годится, иначе «0 failed» нашлось бы в «10 failed». Причина
   непрошедшей так и говорит: «нет строки «…» в выводе (строка
   целиком)».
5. Проверка с полем `не дольше` по истечении срока в минутах прерывается
   вместе с дочерними процессами и не проходит; следующие проверки
   выполняются.
6. По каждой проверке — строка: имя, исход, код выхода, длительность и
   путь полного вывода `.git/branch-kit/check_repo/<имя>.log`; у
   непрошедшей — ещё последние 20 строк вывода. Каталог git средство
   берёт у git: в рабочей копии `git worktree` он свой. Вывод не в UTF-8
   читается по строкам: в Windows — в кодировке OEM, в которой пишут cmd
   и консольные программы, или ANSI, в которой пишут в файл Python и
   программы Windows, — какая из двух даёт больше букв; в Linux — в
   кодировке системы.
7. Последняя строка — итог с вершиной и чистотой рабочей копии.
   Несохранённые изменения — изменённые и новые файлы, которые видит
   `git status`, до проверок или после них: проверка, которая оставила
   файл в рабочей копии, тоже делает итог несохранённым. Итог называет
   отдельно число изменённых отслеживаемых файлов, в том числе
   добавленных `git add`, и число новых — тех, которых git не
   отслеживает и `.gitignore` не исключает, каждого файла, а не
   каталога: новые файлы могла оставить сама проверка.
8. Вершина снимается до проверок и после них. Сменилась — проверка сохранила
   изменение или переключила ветку, и итог не относится ни к одной из двух:
   итог не прошёл, код 1, даже если все проверки прошли, и названы обе
   вершины. Условия поля `успех` и код 0 при неизменной вершине от этого не
   меняются.
9. Файл вывода не открылся — например, в Windows его держит дочерний
   процесс прошлого запуска — или срок `не дольше` больше, чем умеет
   ждать система, например `.inf`: код 2 с именем проверки. Срок
   сверяется до запуска команды.

```
docs: прошла; код выхода 0; 0,4 с; вывод — .git/branch-kit/check_repo/docs.log
build: НЕ ПРОШЛА — нужен код выхода 0; код выхода 1; 12,3 с; вывод — .git/branch-kit/check_repo/build.log
  последние строки вывода (не больше 20):
  | …
проверок 2: прошли 1, не прошли 1; вершина 1a2b3c4d; рабочая копия чистая
```

Если в рабочей копии есть несохранённые изменения, вместо «рабочая копия
чистая» стоит «В РАБОЧЕЙ КОПИИ ЕСТЬ НЕСОХРАНЁННЫЕ ИЗМЕНЕНИЯ» с числами,
например «В РАБОЧЕЙ КОПИИ ЕСТЬ НЕСОХРАНЁННЫЕ ИЗМЕНЕНИЯ: изменённых
отслеживаемых файлов 1, новых файлов 2»: такой итог готовность не
доказывает. Если вершина сменилась, вместо «вершина 1a2b3c4d» стоит:

```
проверок 2: прошли 2, не прошли 0; ВЕРШИНА СМЕНИЛАСЬ ЗА ВРЕМЯ ПРОВЕРОК, ИТОГ НЕ ПРОШЁЛ: до 1a2b3c4d, после 5e6f7a8b; рабочая копия чистая
```

## Формат документов: `check_docs.py`

```
python .branch-kit/tools/check_docs.py [<файл или каталог> …]
```

Проверяет документы по настройке, поле `формат документов` (AGENTS.md,
5.2, 5.4); обычно его выполняет `check_repo.py` как проверку `docs`.

1. Без параметров проверяются файлы, которые отслеживает git и которые
   совпали с масками поля `файлы`. Маска сравнивается с путём от корня
   с учётом регистра букв, как pathspec git (`git ls-files '*.md'`), а
   не как строка `.gitignore`: `*`, `?` и `[!x]` совпадают и с косой
   чертой, `*.md` — все файлы `.md` репозитория, `docs/*.md` берёт и
   файлы во вложенных каталогах `docs/`, а `**` значит то же, что `*`.
   Каталог — его файлы по маскам, которые git отслеживает или видит
   новыми, кроме исключённых `.gitignore`; файл, названный явно,
   проверяется и вне масок. Путь вне клона или несуществующий путь —
   код 2. Ни одного файла для проверки — маска `docs/` вместо `docs/*.md`,
   каталог без файлов по маскам — тоже код 2: «проверка не выполнена»,
   маски и пути названы. Комплект сам приносит файлы `.md`, поэтому ноль
   файлов — ошибка настройки или пути, а итог «нарушений 0» оставил бы
   проверку выключенной навсегда.
2. Что проверяется:

| Вид в выводе | Поле настройки | Что проверяется | В каких файлах |
|---|---|---|---|
| `кодировка` | `кодировка` | UTF-8 с BOM или без, как задано | во всех |
| `концы строк` | `концы строк` | только LF или только CRLF, без смеси и без одиночного CR | во всех |
| `конец файла` | `перевод строки в конце` | в конце файла перевод строки; `false` — не проверяется | во всех |
| `длина строки` | `длина строки` | строки вне таблиц и блоков кода (п. 3) не длиннее; 0 — не проверяется | `.md`, `.markdown` |
| `слово` | `слова` | слово по образцу не употребляется; в выводе — чем его заменить | во всех, кроме самой настройки: в ней слова названы, а не употреблены |
| `ссылка` | `ссылки` | относительная ссылка ведёт на путь, который отслеживает git и который лежит на диске (п. 4); адреса, якоря и ссылки в коде не проверяются | `.md`, `.markdown` |
| `yaml` | `yaml` | файл разбирается безопасным загрузчиком YAML, блок `yaml` в документе — тоже; дата вне календаря, например `2026-02-30`, не разбирается | `.yaml`, `.yml`, блоки в `.md` |
| `блок кода` | — | блок кода закрыт (п. 3); нарушение — на строке, которая его открыла | `.md`, `.markdown` |

3. Блок кода — только огороженный: от строки из трёх и более обратных
   кавычек или тильд до строки только из того же знака, не короче
   открывшей; таблица — строки, которые начинаются с «|». Незакрытый
   блок — нарушение на строке, которая его открыла: он спрятал бы остаток
   файла от длины и ссылок; его блок `yaml` всё равно разбирается.
   Обратные кавычки в сведениях блока не открывают, как в CommonMark:
   строка «```x``` — пример» — обычный текст, и ниже неё всё проверяется.
   Блок с отступом в четыре пробела, примечание HTML `<!-- … -->` и
   строка таблицы без ведущей «|» на длину проверяются как текст: строка
   с отступом в четыре пробела бывает и продолжением пункта списка, и
   пропуск по отступу скрыл бы длинные строки пунктов. Длинную строку в
   таких местах огораживают блоком или начинают строку таблицы с «|».
4. Ссылка ведёт на путь, который отслеживает git и который лежит на
   диске: на файл из `git ls-files`, которого нет в
   `git ls-files --deleted`, или на каталог с такими файлами, с учётом
   регистра букв на любой системе. Файл, удалённый с диска без `git rm`,
   ещё в индексе, но целью не считается: после `git add -A` его не
   будет. Новый файл, который проверяется сам, — назван
   в параметрах или найден в названном каталоге, — тоже годится как
   цель, если его не исключает `.gitignore`: так проверка не ломается до
   первого `git add`. Ссылка на путь в другом регистре букв и на файл,
   которого git не отслеживает, — нарушение и в Windows, где файловая
   система регистр не различает: на площадке такая ссылка не откроется.
   В цели допустимы парные скобки, в том числе вложенные, скобка после
   обратной косой и цель в угловых скобках `<…>` с пробелами. Текст
   ссылки разбирается, как в CommonMark: в нём допустимы парные
   квадратные скобки и картинка, и у ссылки вокруг картинки
   `[![i](a.png)](b.md)` проверяются обе цели. Ссылкой не становятся
   скобки по разные стороны пустой строки и «[», открытая до другой
   ссылки: в `[x [a](a.md)](b.md)` ссылка одна, на `a.md`, — ссылки
   внутри ссылки CommonMark не допускает, и `b.md` не проверяется.
5. Вывод — строка на нарушение `<файл>:<строка>: <вид>: <что не так>`,
   последняя — `нарушений N`. Нет поля `формат документов` — код 2 с
   причиной «формат документов не задан».
6. Файл другого расширения, названный явно или найденный по маске, длину и
   ссылки не проходит (таблица п. 2): чтобы итог не читался как полная
   проверка, перед ним стоит строка с числом таких файлов и примером — первым
   по порядку имён. Код выхода от неё не зависит, строка `нарушений N`
   остаётся последней, и условие `строка в выводе: нарушений 0` проверки
   `docs` работает по-прежнему. Файлы `.yaml` и `.yml` в этом числе тоже: их
   проверяет разбор YAML, но не длина и не ссылки.

```
docs/a.md:12: длина строки: 85 знаков, допустимо 78
docs/a.md:14: слово: «фичи» не употребляется (слово «фича»); вместо — «новая возможность»
файлов без проверки длины строки и ссылок: 1, например notes.txt
нарушений 2
```

## Опрос: `poll.py`

```
python .branch-kit/tools/poll.py --role planner|author|reviewer [--mr <номер>] [--target <ветка>] [--once] [--reset]
```

Ждёт события в очереди роли и завершается на нём, выведя, что произошло
(AGENTS.md, 4.3). Агент держит опрос командой в терминале: ждёт её
завершения, разбирает событие и сразу запускает её снова; завершилась
без события, по сроку, — тоже запускает снова.

| Ключ | Что это |
|---|---|
| `--role` | роль: `planner` — постановщик, `author` — автор, `reviewer` — проверяющий; учётная запись ключа сверяется с этой ролью в настройке, с `--target` — с авторами |
| `--mr` | у автора обязательно: номер своего запроса; запрос, поданный другой учётной записью, — отказ с кодом 2 |
| `--target` | только у роли `reviewer`: очередь проверяющего частей — открытые запросы в названную корневую ветку задачи вместо основной (AGENTS.md, 3.7); у `planner` и `author`, с основной веткой или пустым именем — отказ с кодом 2 до обращения к площадке. Ветка сверяется при каждом запуске (`repository/branches/<цель>`): её нет — код 2 с именем ветки, иначе опечатка оставила бы очередь пустой навсегда; ветка есть, запросов в неё нет — `событий 0` |
| `--once` | одно обращение без ожидания: вывести события с прошлого раза и завершиться — для сверки вручную |
| `--reset` | забыть запомненное состояние и завершиться, не обращаясь к площадке; следующий запуск — как первый |
| `--host` | другая площадка вместо поля `площадка`, `адрес` настройки |
| `--config` | другая настройка |

| Роль | Чьи запросы | События |
|---|---|---|
| постановщик | открытые запросы в основную ветку (поле `основная ветка`) | новый запрос; новая заметка в открытом запросе; слияние или закрытие запроса; смена цели запроса (п. 8) |
| автор | свой запрос | новая заметка, смена вершины ветки, смена утверждений, слияние, закрытие, новое открытие; у запроса части — в том числе свои заметки и отправки (п. 1) |
| проверяющий | открытые запросы в основную ветку (поле `основная ветка`), кроме черновиков (п. 10) | новый запрос; новая заметка в открытом запросе; смена вершины ветки открытого запроса; смена утверждений; снятие и постановка пометки черновика; смена цели запроса (п. 8) |
| проверяющий частей: `--role reviewer --target <корневая ветка>` | открытые запросы в корневую ветку, кроме черновиков (п. 10) | те же, что у проверяющего, в том числе свои заметки и отправки (п. 1) |

Фильтр по цели запроса ставит сама площадка: список открытых запросов
средство просит с полем `target_branch` — основной ветки из настройки
или ветки из `--target`. Запрос части в корневую ветку постановщику и
проверяющему не виден: ни новым запросом, ни заметкой, ни слиянием.
Черновики из очереди проверяющего отбирает само средство (п. 10).

1. Своё событием не считается: заметка учётной записи ключа и смена
   вершины ветки на изменение, сохранённое подписью роли из настройки
   (`учётные записи`, `подпись`, `почта`): почта того, кто сохранил
   изменение (у git — committer), совпадает с почтой подписи — это своя
   отправка. Чужое изменение — событие, даже если оно уже есть в
   локальной ветке клона: проверяющий берёт ветку в свою локальную
   ветку, чтобы проверить результат слияния (AGENTS.md, 2.6), а автор —
   правку проверяющего. Вершина, которой в клоне нет, — тоже событие.
   Почта в настройках git клона расходится с подписью в настройке —
   своя отправка тоже станет событием: лишним, но не потерянным. У
   проверяющего частей и у автора запроса части своё — тоже событие: они
   могут работать под одной учётной записью автора (AGENTS.md, 1.5, 3.7),
   и своё от чужого опрос не отличит. Запрос части — запрос, цель которого
   в ответе площадки не основная ветка; у автора запроса в основную ветку
   своё по-прежнему не событие. Своя заметка или отправка вернётся
   событием один раз: лишнее событие дешевле пропущенного замечания.
2. Системные заметки площадки, например «added 1 commit» или «approved
   this merge request», событием не считаются: то, о чём они, опрос
   ловит отдельно — смену вершины, утверждений, слияние.
3. Период обращений к площадке — настройка, поле `опрос`, `период`, в
   минутах. `не дольше` больше нуля — через столько минут опрос
   завершается без события с кодом 1, чтобы его подняли снова; если за
   этот срок не удалось ни одно обращение — с кодом 2 (п. 6).
4. Состояние, с которым сравниваются ответы площадки, хранится в клоне,
   вне отслеживаемых файлов:
   `.git/branch-kit/poll/<роль>[-<номер>][-<корневая ветка>].json`;
   имя корневой ветки записано с заменой `/` и других знаков на `%XX`,
   например `reviewer-feat%2Fvp-import.json`, и у очереди частей каждой
   корневой ветки свой файл. Оно записывается после вывода событий:
   прерванный между выводом и записью запуск покажет те же события
   снова, но не потеряет их.
   Событие, случившееся, пока опрос не был поднят, следующий запуск
   покажет. Файл состояния не записался или `--reset` его не удалил —
   например, в Windows его держит открытым другой процесс, второй опрос
   той же роли из этого клона, — код 2 с путём к файлу; выведенные
   события следующий запуск покажет снова.
5. Первый запуск без состояния выводит исходное состояние — открытые
   запросы, у автора — свой запрос, их вершины и последние заметки — как
   событие и завершается с кодом 0: роль сверяет очередь вручную
   (AGENTS.md, 4.3). У проверяющего черновиков в исходном состоянии нет;
   когда открыты только черновики, их номера названы в строке «открытых
   запросов в <ветка> нет, кроме черновиков: !12».
6. Сбой площадки во время ожидания — нет ответа или ошибка сервера — это
   строка в потоке ошибок и повтор на следующем периоде; пять сбоев
   подряд — код 2 с причиной. Срок `не дольше` вышел раньше пятого сбоя, а
   все обращения этого запуска сбойные — тоже код 2 с последним сбоем, а не
   код 1 «срок вышел без событий»: счётчик сбоев живёт один запуск, и код 1
   скрывал бы молчащую площадку при каждом новом запуске. Хоть одно обращение
   удалось, в том числе после сбоя или до него, — код 1. Отказ площадки — ключ
   не принят, нет проекта или запроса — сразу код 2; удалённый запрос у
   постановщика — событие (п. 8). С `--once` и при первом обращении любой
   сбой — сразу код 2.
7. Состояние, записанное для другой площадки, репозитория, роли,
   запроса или цели, и испорченное состояние, в том числе запись запроса
   не того вида, — код 2 с путём к файлу и советом начать заново ключом
   `--reset`. Так же — состояние постановщика или
   проверяющего без поля `цель`: его записала версия средства без
   фильтра по цели, и в нём могут быть запросы частей. После обновления
   комплекта до версии с фильтром постановщик и проверяющий начинают
   опрос заново ключом `--reset`.
8. Запрос, пропавший из списка открытых, постановщик и проверяющий, в том
   числе проверяющий частей, перечитывают по номеру — одним обращением на
   пропавший запрос, а не на каждый запрос каждого круга:
   - открыт, а цель другая — событие «цель сменена: main → feat/other — вне
     очереди» у обоих, один раз; дальше опрос запрос не ведёт и по номеру не
     читает. Цель вернут — запрос придёт новым запросом. Черновик, который и
     до смены цели был черновиком, проверяющему событий не даёт (п. 10);
   - открыт с той же целью — запрос успели закрыть и снова открыть между двумя
     ответами площадки: событий нет, запрос остаётся в очереди;
   - слит или закрыт — у постановщика событие с тем, кто это сделал, у
     проверяющего молча: проверяющему такой запрос не нужен;
   - площадка отвечает 404 — запрос удалили: у постановщика событие
     «удалён», у проверяющего молча; дальше опрос его не ведёт.
9. Новые заметки читаются страницами по 100, от новых к старым; заметка,
   пришедшая между чтением двух страниц, сдвигает их, и повтор на
   соседней странице отбрасывается: каждая заметка — одно событие.
10. Черновик — работа автора (AGENTS.md, 3.7, пп. 1, 7), и проверяющий,
    в том числе проверяющий частей, его не ведёт. Черновик — запрос, у
    которого в ответе площадки поле `draft` — истина или имя начинается
    с «Draft:»: по имени черновик узнаётся и на площадке без этого поля.
    Новый черновик, заметки в нём, смена его вершины и утверждений
    событий не дают. Снятие пометки — событие «снята пометка черновика —
    на проверке», вслед за ним — заметки и смены, пришедшие с прошлого
    обращения; дальше запрос — как любой. Пометка, поставленная запросу
    на проверке, — событие «поставлена пометка черновика — до её снятия
    событий нет», вслед за ним — заметки, написанные до пометки в том же
    промежутке, и смена утверждений этого промежутка: при снятии пометки
    их уже не показать. Заметка до или после пометки — по системной заметке
    площадки «marked this merge request as \*\*draft\*\*»: заметка после неё
    молчит; такой заметки нет — порядок не определить, и заметка
    показывается: лишнее дешевле потерянного. Смена утверждений показывается
    всегда: когда её сделали, площадка в ответе не говорит. Смена вершины того
    же промежутка не показывается: снятие пометки и так велит прочитать запрос
    заново. В состоянии, записанном до отбора черновиков,
    признака черновика нет: открытый черновик из него один раз даст
    событие постановки пометки. Постановщик и автор видят черновик, как
    любой запрос: в черновике автор задаёт вопрос постановщику
    (AGENTS.md, 1.6).

```
[14:05:12] !12 заметка 3456 от ai-reviewer: Модель проверяющего: …
[14:05:12] !12 вершина ветки 1a2b3c4d → 5e6f7a8b
[14:05:12] !12 утверждения: добавил root
[14:05:12] !13 новый запрос «…» от ai-dev, ветка fix/login-timeout
[14:05:12] !14 снята пометка черновика — на проверке
[14:05:12] !15 цель сменена: main → feat/other — вне очереди
[14:05:12] !11 слит, слил ai-reviewer
событий 7
```

## Журнал слияний: `check_merge_log.py`

```
python .branch-kit/tools/check_merge_log.py [--host <адрес>] [--config <файл>]
```

Проверяет, что основная ветка менялась только по правилам разделов 2 и
3 AGENTS.md. Читает через API площадки первую линию основной ветки,
слитые в неё запросы, их утверждения и заметки; на площадке ничего не
меняет.

| Вид | Что проверяется |
|---|---|
| `не слиянием` | каждое изменение первой линии основной ветки пришло слиянием запроса (AGENTS.md, 3.1) |
| `склейка` | запрос слит способом merge, без склейки (2.4): у слитого запроса нет изменения склейки (поле `squash_commit_sha`) и не включён флаг `squash` |
| `сливший автор` | запрос слил не его автор (1.3); площадка не назвала, кто слил, — тоже нарушение |
| `нет варианта решений` | в разделе «Решения» описания ровно один вариант шаблона (2.3) |
| `нет утверждения владельца` | запрос «несёт новое решение» утверждён владельцем (2.2) |
| `нет прямого следа` | у запроса «исполняет решение владельца» есть утверждение владельца, его заметка в запросе или однозначная ссылка на запрос с ними (2.5) |
| `повторная ветка` | ветку запроса не использовал другой, раньше слитый запрос (3.5) |
| `нет на первой линии` | изменение слияния каждого слитого запроса (поле `merge_commit_sha`) лежит на первой линии: иначе историю основной ветки перезаписали — заменили или откатили (3.4); запрос с пустым полем так не сверить, это не нарушение |

1. Владелец — настройка, поле `учётные записи`, `владелец`. След в
   названном запросе — утверждение или заметка того же владельца, и в
   другом репозитории группы тоже: решение по этому репозиторию даёт его
   владелец (AGENTS.md, 1.1). Системная заметка площадки, например
   «mentioned in merge request», следом не считается.
2. Первая линия — изменения от вершины основной ветки по первому
   родителю. Начальное изменение без родителей, которое площадка создаёт
   при заведении проекта, не проверяется. Первая линия, полученная от
   площадки не целиком, — код 2: непроверенная часть истории иначе
   прошла бы молча. Так же — изменение первой линии без поля `parent_ids`
   или с полем не списком: пустой список значит начальное изменение, и
   конец линии иначе был бы неотличим от начала истории.
3. Раздел «Решения» — от заголовка «Решения» до следующего заголовка;
   заголовок узнаётся и с двоеточием, и с закрывающими «#»:
   `## Решения:`, `## Решения ##`. Комментарии HTML и блоки кода не
   читаются: заголовок в блоке кода выше настоящего раздела раздел не
   подменяет. Заборы блоков — как у `check_docs.py`. Начало комментария
   в строчном коде — в обратных кавычках в пределах одной строки —
   комментарий не открывает: иначе он тянулся бы до конца комментария в
   подвале шаблона и съедал раздел. Настоящий комментарий скрыт, и с
   заголовком «Решения» внутри. Вариант — строка раздела, которая
   начинается словами варианта из шаблона запроса.
4. Ссылка на запрос засчитывается следом, только если узнаётся
   однозначно: `!5` — запрос этого репозитория;
   `<группа>/<репозиторий>!5` и `<группа>/<репозиторий> !5`, в том числе
   с именем в кавычках или скобках, с двоеточием перед номером и с
   перечислением `!5, !6 и !7`, — запрос названного репозитория своей
   группы; адрес запроса на этой площадке — с узлом из адреса площадки
   или из адресов запросов в ответах площадки, без схемы или путём от
   корня `/<группа>/<репозиторий>/-/merge_requests/5`. У адреса без
   схемы первый сегмент с точкой — узел, если адрес не начинается своей
   группой: в имени группы тоже бывает точка
   (`tmi.ru/sub/x/-/merge_requests/5` при группе `tmi.ru`). Адрес запроса в
   ответе площадки, узел которого не разбирается, — код 2 с этим адресом
   в причине: это сбой ответа площадки, а не нарушение правил
   репозитория, и без этого узла ссылки с ним не узнавались бы.
5. Не засчитываются: репозиторий вне своей группы, адрес другой
   площадки, адрес, узел которого не разбирается (например, с
   незакрытой квадратной скобкой: `http://[::1/…`), ссылка в блоке кода
   между ``` или ~~~, текст ссылки Markdown
   (засчитывается её адрес), номер сразу после пути файла и любой номер
   без имени репозитория, если раздел называет другой репозиторий
   группы. Ложное «нет прямого следа» разбирают исключением, а ложный
   след прошёл бы молча.
6. Уже слитое нарушение разбирают исключением (раздел «Разобранные
   исключения»): историю основной ветки не переписывают (AGENTS.md,
   3.4).

Вывод — сначала строка о том, что проверено, затем строка на нарушение
`<где>: <вид>: <что не так>`, где — `!N` у запроса или первые 8 знаков
изменения; последняя — `нарушений N`:

```
основная ветка main репозитория example/app: изменений первой линии 11, слитых запросов 9; владелец — owner
33333333: не слиянием: изменение «правка прямо в основную ветку» пришло в main не слиянием запроса
!3: сливший автор: слил сам автор запроса ai-dev
нарушений 2
```

## Защита веток: `owner_protect_branches.py`

**Запускает только владелец** своим ключом в `GITLAB_TOKEN`: настройки
проекта меняет только он (AGENTS.md, 3.4). Запускают, когда запрос с
комплектом слит и префиксы веток задач есть в основной ветке.

```
python .branch-kit/tools/owner_protect_branches.py [--dry-run] [--host <адрес>] [--config <файл>]
```

1. Учётная запись ключа — не владелец по настройке — код 2: правила не
   читаются и не ставятся.
2. По каждому префиксу из поля `ветки задач` ставится правило
   `<префикс>*`: отправка и слияние — Developer и Maintainer,
   принудительная отправка запрещена.
3. Правило, которое уже есть, не меняется: совпадает с нужным — «без
   изменений», отличается — расхождение, которое владелец правит сам в
   Settings → Repository → Protected branches. Повторный запуск поэтому
   ничего не меняет.
4. Основную ветку и настройки слияния средство только сверяет.
   Основная ветка — отправка «No one» (никто), слияние «Maintainers»,
   принудительная отправка запрещена; другое правило, маска которого
   подходит к основной ветке, — тоже расхождение: из подходящих правил
   GitLab берёт самое мягкое. Способ слияния — merge commit (`merge`);
   склейка — `never`, «Do not allow»: запрещена; `default_off` —
   расхождение: склейка не включена по умолчанию, но разрешена; ветка
   после слияния по умолчанию не удаляется. Поле, которого нет в ответе
   площадки, — расхождение: «как нужно» тогда не доказано.
5. По каждому правилу печатается «было — стало»; «стало» — правило,
   перечитанное у площадки после создания, а не то, что средство
   просило.
6. `--dry-run` ничего не меняет и показывает, что было бы сделано; код
   при нём — 1, если хоть одно правило ещё нужно создать.

```
учётная запись ключа: owner — владелец по настройке; репозиторий example/app
ветки docs/*: было — нет правила; стало — отправка: Developer и Maintainer; слияние: Developer и Maintainer; принудительная отправка: запрещена
ветки feat/*: было — отправка: Developer и Maintainer; слияние: Developer и Maintainer; принудительная отправка: запрещена; стало — без изменений
основная ветка main: было — отправка: никто; слияние: Maintainer; принудительная отправка: запрещена; стало — без изменений, средство её только сверяет — как нужно
способ слияния: merge — как нужно
склейка при слиянии: never — как нужно
удаление ветки после слияния по умолчанию: выключено — как нужно
итог: правил веток задач 2: создано 1, без изменений 1; расхождений 0
```

## Проверка настройки попыткой: `owner_check_settings.py`

**Запускает только владелец.** Попытка делается ключом той учётной
записи, чьи права проверяются; чужим ключом работает только владелец и
только для этого, каждый раз с записью в протокол (AGENTS.md, 6.6).
Средство ничего не настраивает и не удаляет; ключ владельца ему не
нужен. Кроме попыток, ключом автора средство читает площадку и ведёт
пробный запрос — все его действия этим ключом названы в п. 6 ниже.
Запускают после защиты веток задач и после каждого изменения настроек
проекта и участников.

```
python .branch-kit/tools/owner_check_settings.py --developer-key <файл> [--maintainer-key <файл>] [--planner-key <файл>] [--host <адрес>] [--config <файл>]
```

| Ключ | Что это |
|---|---|
| `--developer-key` | обязательно: файл ключа учётной записи автора (Developer) |
| `--maintainer-key` | необязательно: файл ключа проверяющего (Maintainer); без него попытка б) — «не проверялось» |
| `--planner-key` | необязательно: файл ключа постановщика (Reporter); без него попытки е) и ж) — «не проверялось» |

Ключи — только из файлов, вне репозитория (AGENTS.md, 7.2); края файла
отбрасываются, как у `GITLAB_TOKEN`; файл с другими знаками или с меткой
порядка байтов — код 2. Один и тот же ключ на две роли — код 2.

До первой отправки средство сверяет; не сошлось — код 2, ни одной
отправки:

1. Учётная запись каждого ключа — та, что у его роли в настройке, поле
   `учётные записи`: у автора — одна из `авторы`.
2. Её уровень в проекте — ровно Developer, Maintainer и Reporter, с
   учётом членства через группы (API `members/all`).
3. Не администратор. Поле `is_admin` площадка показывает только
   администратору, поэтому сверка ещё и по настройкам площадки, которые
   читает только администратор: ключ их прочёл — администратор, код 2;
   ответ 403 — нет; другой ответ — «не проверялось», это пишется во
   фрагмент протокола, и запуск идёт дальше.
4. Адрес хранилища — `<адрес площадки>/<группа>/<репозиторий>.git` из
   настройки или `--host`: без учётных данных и не переписан настройкой
   git `url.*.insteadOf`.
5. Подпись пробных изменений — `user.name` и `user.email` из настроек
   git клона: того, кто запускает.

| Попытка | Ключ | Ожидаемый исход | Отказ засчитан, если в ответе площадки |
|---|---|---|---|
| а) отправка в основную ветку | автора | отказ | `not allowed to push code to protected branches` |
| б) принудительная отправка в основную ветку | проверяющего | отказ | `not allowed to force push code to a protected branch` |
| в) отправка пробной ветки `test/settings-check-<дата>[-N]` | автора | проходит | — |
| г) принудительная отправка в пробную ветку | автора | отказ | `not allowed to force push code to a protected branch` |
| д) удаление пробной ветки | автора | отказ | `not allowed to delete protected branches` |
| е) отправка в пробную ветку | постановщика | отказ | `not allowed to push code` |
| ж) заметка в запросе из пробной ветки | постановщика | проходит | — |
| з) слияние запроса из пробной ветки | автора | отказ; затем запрос закрывается, не удаляется | код ответа API 401 или 403 |

1. Пробная ветка берёт префикс `test/`, а если его нет в поле
   `ветки задач`, — первый префикс оттуда; занято имя с датой —
   добавляется `-2`, `-3` и дальше. Ветка остаётся на площадке: ветки не
   удаляют (AGENTS.md, 3.4).
2. Перед каждой попыткой средство снимает свежую копию ветки во
   временный каталог. Принудительная отправка и удаление идут с
   `--force-with-lease` на вершину копии: чужое изменение, легшее между
   копией и попыткой, не затирается — попытка «НЕ ВЫПОЛНЕНА — ветка ушла
   с вершины копии». Тот же исход у обычной отправки а) и е) в ушедшую
   ветку: её git отклоняет сам, до площадки, строкой
   `! [rejected] … (fetch first)` или `(non-fast-forward)`. Такая
   попытка настройку не проверила, поэтому она тоже расхождение: оно
   входит в «расхождений N» итога, код выхода 1. Повторите запуск, когда
   в ветки никто не отправляет.
3. Отказ засчитывается, только если ответ площадки содержит строку из
   таблицы, у слияния — код ответа 401 или 403. Отказ другим ответом
   настройку не подтверждает: «ОТКАЗ НЕ ТЕМ ОТВЕТОМ — НЕ КАК ОЖИДАЛОСЬ».
4. Прошла попытка переписать ветку или удалить её — ветка возвращается
   на вершину копии тем же ключом, с `--force-with-lease` на изменение
   попытки. Прошла обычная отправка или слияние — не откатывается:
   строка «ВЕТКА … ОСТАЛАСЬ ИЗМЕНЕНА» с вершинами и советом. У основной
   ветки совет — отменить изменение новым запросом и исправить
   настройку; у пробной ветки после е) — исправить настройку, а
   изменение можно оставить: пробную ветку не сливают. В такую ветку
   запуск больше не пишет, а копия остаётся на диске; вершина ветки до
   попытки лежит в копии ссылкой `refs/before/<ветка>`. Ветку, которую
   удалили не этой попыткой, средство не воссоздаёт.

   Возврат из копии не вышел, а на ветке по-прежнему изменение
   попытки, — совет вернуть ветку командой, которую средство печатает в
   итоге в двух формах: для Linux и Git Bash и для PowerShell. Команда
   написана по AGENTS.md, 6.4: пустая запись, свой помощник, который
   читает файл ключа, и запрет переадресации. У копии своих настроек
   нет, и без них git пошёл бы к площадке через глобальный или
   системный помощник учётных данных машины — чужой учётной записью. В
   `<файл ключа>` подставляют путь к файлу своего ключа владельца, через
   `/`: команду владелец выполняет сам, вне средства, а чужим ключом вне
   средства не работают (AGENTS.md, 6.6). Своего права ему хватает:
   такой совет бывает только после того, как защита пропустила
   принудительную отправку или удаление ключом автора или проверяющего,
   а права владельца не ниже. Ветка после попытки ушла дальше — команды
   нет, совет — восстановить её из копии вручную, сохранив чужие
   изменения.
5. Сбой или Ctrl+C после первой отправки копию не удаляет: печатаются
   «ЗАПУСК ПРЕРВАН ПОСЛЕ ОТПРАВОК», вершины веток до попыток и путь к
   копии.
6. Пробные изменения пустые; каждая отправка идёт с `-o ci.skip`, чтобы
   не запускать конвейер. Каждым ключом средство сверяет его учётную
   запись (сверки 1–3 выше) и делает его попытки, а после прошедшей
   попытки переписать или удалить ветку — возврат из копии (п. 4).
   Ключом автора, кроме того, идут все остальные обращения к площадке:
   средство читает вершины веток (`git ls-remote`), снимает копии веток
   (`git fetch`), читает правила защиты для фрагмента протокола,
   создаёт пробный запрос, после отказа в попытке з) сверяет, не слит ли
   он всё же, и закрывает его. Правила защиты площадка может ключу
   автора не отдать: тогда в выводе — «правила защиты не прочитаны» с её
   ответом, во фрагменте — «не прочитаны», а попытки идут дальше. На
   площадке с GitLab 17.11.2, бесплатной редакцией, ключ Developer
   правила прочёл. Пробный запрос (заголовок «test: проверка настройки
   попыткой — пробный запрос, не сливать») и заметку ж) постановщик и
   проверяющий увидят своим опросом. Проверяющий такой запрос не берёт
   и на заметку не отвечает: средство закрывает запрос само.
7. Ключ git получает помощником учётных данных из переменной окружения
   `BRANCH_KIT_CHECK_KEY`, заданной только процессу git; перед
   помощником стоит пустая запись (AGENTS.md, 6.4). Из окружения git не
   получает трассировку (`GIT_TRACE…`, `GIT_CURL_VERBOSE`), настройки
   `GIT_CONFIG…`, каталоги `GIT_DIR`, `GIT_WORK_TREE` и подобные,
   `GIT_ASKPASS`, `SSLKEYLOGFILE`, `GITLAB_TOKEN` и переменные ключей из
   настройки; заголовки `http.extraHeader` — общие и для адреса
   хранилища — сбрасываются. По переадресации git не идёт
   (`http.followRedirects=false`): помощник отдал бы ключ роли другому
   узлу. Площадка ответила переадресацией до попыток — код 2 с
   причиной, во время попытки — расхождение с дословным ответом git.

Вывод — строка на попытку и дословный ответ площадки; после попыток —
ветки, оставшиеся изменёнными, вершины веток, итог и фрагмент протокола
в YAML. Над фрагментом — имя файла
`.branch-kit/protocols/<дата>-<номер>.yaml`; что во фрагменте и как его
вносят — `.branch-kit/protocols/README.md`.

```
[14:05:12] а) отправка в основную ветку main — ключ автора ai-dev — код 1 — отказ — как ожидалось
    ответ площадки: remote: GitLab: You are not allowed to push code to protected branches on this project. | …
…
итог: всё как ожидалось; отказ — как ожидалось — а), б), г), д), е), з); прошла — как ожидалось — в), ж)

--- фрагмент протокола для .branch-kit/protocols/2026-10-10-1.yaml ---
что проверено: настройка площадки попыткой (AGENTS.md, 6.6)
…
```

Чего средство не проверяет:

1. Права учётных записей, ключей которых нет в запуске, в том числе
   людей.
2. Защиту веток задач, кроме пробной: их правила видны во фрагменте
   протокола.
3. Удаление ветки запросом API.
4. Слияние без утверждения владельца: бесплатная редакция GitLab его не
   останавливает, это держат проверяющий и `check_merge_log.py`.
5. Администратора, если площадка на чтение своих настроек ответила не
   200 и не 403: тогда «не проверялось». Ответ 403 ключам ролей, не
   администраторов, проверен на площадке с GitLab 17.11.2, бесплатной
   редакцией. Ключ администратора, которому площадка не даёт прав
   администратора без режима Admin Mode, сверку «не администратор»
   пройдёт; на площадке это не проверено.
6. Строку отказа Reporter `not allowed to push code` средство берёт из
   документации GitLab. На площадке с GitLab 17.11.2, бесплатной
   редакцией, отказ пришёл с ней: «You are not allowed to push code to
   this project.». Другая редакция или версия GitLab может ответить
   иначе; тогда попытка даст «ОТКАЗ НЕ ТЕМ ОТВЕТОМ», и строку сверяют с
   ответом своей площадки.

## Разобранные исключения

Нарушение, которое нарушением не является, разбирают записью в
`.branch-kit/exceptions.yaml`: поля и пример — в самом файле. Исключения
читают `check_docs.py` и `check_merge_log.py`; запись снимает нарушение
своего вида у своего средства в месте `место`:

1. У `check_docs.py` место — путь файла от корня клона, а с полем
   `абзац` запись действует только в абзаце, в тексте которого есть эти
   слова.
2. У `check_merge_log.py` место — запрос `"!<номер>"` или изменение
   основной ветки — первые 8 знаков его обозначения в git, в кавычках:
   как в выводе средства. Абзаца у него нет: запись действует на запрос
   или изменение целиком.
3. Исключение без причины, с неизвестным полем, средством или видом, с
   местом не того вида — нарушение вида `исключение`, и оно ничего не
   снимает.
4. Исключение, которое при полной проверке, без параметров, ничего не
   покрыло, — нарушение: его убирают или поправляют.
5. Новое исключение — решение: его вносят запросом с утверждением
   владельца (AGENTS.md, 2.2, 2.3).

## Проверки самих средств

Проверка, которая не замечает порчу, ничего не доказывает (AGENTS.md,
4.7). В `tests/` на каждый вид нарушения и каждый код выхода есть
испорченный вход, и проверки показывают, что он пойман. Запуск из корня
клона:

```
python -B -m unittest discover -s .branch-kit/tools/tests -v
```

1. Средства копируются во временный клон git, как в репозиторий с
   комплектом, и запускаются отдельным процессом; испорченные файлы
   создаются там же при каждом запуске.
2. Площадку изображает поддельная площадка `tests/fake_api.py` — сервер
   на `127.0.0.1` с записанными ответами `tests/answers.json`; к
   настоящей площадке проверки не обращаются. В каждой проверке с ключом
   сверяется, что ключ не попал в вывод. Для проверок TLS поддельная
   площадка отвечает и по https: ключ и сертификат на `127.0.0.1`
   выпускает `tests/fake_tls.py` средствами стандартной библиотеки во
   временный каталог проверки, а клиент доверяет сертификату через
   переменную `SSL_CERT_FILE`.
3. Средства запускаются с кодировкой вывода `ascii`, в которой русский
   текст не выводится, и с несуществующим прокси, а `127.0.0.1` назван в
   `NO_PROXY` сетью: так проверяется, что вывод — UTF-8 и что узел из
   `NO_PROXY` идёт мимо прокси. Системный прокси изображает вторая
   поддельная площадка: функции urllib, которые в Windows читают прокси
   из реестра, подменены на её адрес, а в Linux, где их нет, созданы.
   Проверка показывает, что без переменных `*_PROXY` клиент идёт к
   площадке напрямую и ключ к системному прокси не приходит.
4. Ctrl+C проверяется в том же процессе: отдельному процессу его надёжно
   не послать в обеих системах. Проверки, которые выполняют средство в
   том же процессе, подменяют окружение целиком (`helpers.patch_env`),
   чтобы переменные машины, в том числе строчная `no_proxy` в Linux, не
   просочились; проверка `InProcessEnvTest.test_like_linux` изображает
   окружение, различающее регистр имён, как в Linux.
5. Журнал слияний — по записанным ответам `tests/merge_log_answers.json`
   с одним нарушением каждого вида, кроме склейки: её проверка ставит
   полем слитого запроса; замену и откат основной ветки проверки ставят
   поверх чистой истории, — и по таблице записей ссылок на запрос:
   верные засчитаны, неоднозначные нет; ловушка — номер, у которого след
   есть в своём репозитории, но нет в названном.
6. Защита веток — первый запуск, повторный, отличающееся правило,
   правило, которое площадка сохранила не так, ключ не владельца.
7. Проверка настройки попыткой — на локальных хранилищах `file://`:
   защиту площадки изображает приёмный перехватчик `pre-receive` с её
   ответами, а запросы, заметку и слияние — поддельная площадка. По
   журналу перехватчика сверяется, что каждая отправка шла с `ci.skip`
   и что переменные окружения владельца до git не дошли; что заголовки
   сброшены, ключ git получил своим помощником и по переадресации на
   другой узел не пошёл — по записанным обращениям git к поддельным
   серверам по `http`. Средство выполняется
   в том же процессе: так в ход попыток вставляются чужое изменение,
   удаление ветки, сбой и Ctrl+C, а адрес хранилища подменяется на
   `file://`.
8. Проверки, в которых git работает с хранилищами `file://`, в Git Bash
   выполняют без переменной `MSYS_NO_PATHCONV`: при `MSYS_NO_PATHCONV=1`
   путь вида `/C:/…` не переводится, и git не находит хранилище:

```
env -u MSYS_NO_PATHCONV python -B -m unittest discover -s .branch-kit/tools/tests -v
```
